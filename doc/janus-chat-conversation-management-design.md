# JanusX Chat 多对话管理设计方案

> 状态：设计提案，不包含实现
> 范围：Island Chat 与工作区嵌入 Chat 共用同一套对话数据和管理交互
> 设计基线：延续现有深色、终端感、橙色强调的 JanusX Chat，不引入新的视觉体系

## 1. 目标

把当前“单条临时线程”升级为可持续使用的多对话系统，同时保持 Island Chat 的轻量感。

用户需要能够：

- 新建、切换、重命名和删除对话。
- 在 Island 与工作区嵌入窗口之间继续同一条对话。
- 快速定位最近对话，并明确知道当前正在使用哪一条。
- 保留每条对话的模型选择、工作区资源和消息历史。
- 在误删、流式生成或配置变化时得到可预期的结果。

本方案不包含：对话分支、多人协作、云同步、跨设备同步、对话分享和文件夹体系。这些能力不进入第一版。

## 2. 设计原则

1. **对话是主对象**：模型、资源、消息和运行状态都归属于对话，不再挂在一个全局 Chat 状态上。
2. **一个控制器，多种呈现**：Island 与嵌入窗口只是同一控制器的两个视图，不复制消息和选择状态。
3. **最近对话优先**：默认展示最近使用的对话，管理入口不长期占用主要内容宽度。
4. **删除可恢复**：普通删除先软删除并提供撤销，避免使用高频确认弹窗打断操作。
5. **状态必须可见**：生成中、失败、未发送草稿和已删除状态都必须在列表中有明确反馈。
6. **沿用现有视觉语言**：使用清晰分隔、紧凑行高和单一橙色焦点，不增加装饰性渐变、发光卡片或大量图标。

## 3. 信息架构

```text
Janus Chat
├─ 当前对话标题 / 对话管理入口
├─ 对话列表
│  ├─ 新建对话
│  ├─ 搜索
│  ├─ 今天
│  ├─ 昨天
│  └─ 更早
├─ 当前对话
│  ├─ 消息
│  ├─ 工作区资源
│  ├─ 模型选择
│  └─ 输入草稿
└─ 已删除对话（第一版仅保留恢复能力，不提供常驻入口）
```

## 4. 界面方案

### 4.1 顶部入口

把当前工具栏中的 `Thread / Janus` 改为可点击的对话标题区域：

- 第一行仍显示 `Thread`。
- 第二行显示当前对话标题，单行截断。
- 标题右侧显示小型展开标记。
- 点击标题打开对话管理面板。
- 标题区域旁保留一个明确的 `+` 新建按钮。

标题初始取第一条用户消息的前 28 个可见字符；生成标题前显示“新对话”。用户重命名后不再自动覆盖。

### 4.2 对话管理面板

推荐采用覆盖式侧面板，而不是永久侧栏：

- Island 展开态：面板从 Chat 左侧内容区覆盖出现，宽度约 280px，不改变 Island 整体尺寸。
- 工作区宽度大于 960px：允许面板固定在左侧，宽度 260–300px。
- 工作区较窄：降级为与 Island 相同的覆盖面板。

面板结构从上到下为：

1. `新建对话` 主操作。
2. 搜索输入框，只搜索标题和用户消息摘要。
3. 按“今天 / 昨天 / 最近 7 天 / 更早”分组的对话列表。
4. 每行展示标题、最后更新时间和状态点。
5. 行尾操作菜单提供“重命名”和“删除”。

当前对话使用 2px 橙色左标和更高文本对比度表达，不整行铺橙色背景。生成中的对话使用低频脉冲状态点；失败状态使用静态红点，避免持续动画。

### 4.3 对话行状态

| 状态 | 列表表现 | 允许操作 |
|---|---|---|
| 普通 | 标题 + 相对时间 | 切换、重命名、删除 |
| 当前 | 橙色左标 | 重命名、删除 |
| 生成中 | 小型动态状态点 + `生成中` | 切换、停止后删除 |
| 失败 | 红色静态点 + `失败` | 打开、重试、删除 |
| 有草稿 | 标题后显示 `草稿` | 打开、删除 |
| 已删除 | 默认不显示 | 撤销或到期清理 |

## 5. 核心交互流程

### 5.1 新建对话

1. 用户点击 `+` 或面板中的“新建对话”。
2. 创建空对话并立即切换。
3. 输入框获得焦点。
4. 新对话默认跟随当前 LLM 默认供应商与默认模型。
5. 第一条用户消息提交后生成本地标题。

如果当前对话为空且没有草稿，再次点击新建不重复创建，而是保持当前空对话。

### 5.2 切换对话

1. 打开管理面板并点击目标对话。
2. 面板关闭，消息区恢复该对话的滚动位置和草稿。
3. Island 和嵌入窗口同步显示新的当前对话。

目标设计允许后台对话继续生成。第一阶段若运行时尚未支持并行流，则生成期间切换时显示小型确认条：`停止当前生成并切换 / 取消`，不使用居中模态框。

### 5.3 重命名

- 从行尾菜单进入原位编辑。
- `Enter` 保存，`Esc` 取消。
- 去除首尾空格，空标题不保存。
- 最长 80 个字符，列表单行显示，完整标题通过悬停提示查看。

### 5.4 删除

普通对话采用软删除：

1. 点击“删除”后立即从列表移除。
2. Chat 底部显示 5 秒撤销条：`已删除“标题” · 撤销`。
3. 软删除数据保留 7 天，之后清理。
4. 删除当前对话后自动进入最近一条未删除对话；如果没有则创建新的空对话。

生成中的对话必须先确认：`此对话仍在生成。停止并删除？`。确认后停止流、释放该对话的运行资源，再执行软删除。

## 6. 快捷键设计

快捷键仅在焦点位于 Chat 界面内部时生效，避免覆盖编辑器和终端：

| 快捷键 | 行为 |
|---|---|
| `Ctrl+Shift+N` | 新建对话 |
| `Ctrl+K` | 打开对话管理并聚焦搜索 |
| `Tab` | 打开供应商菜单 |
| `Ctrl+P` | 打开模型菜单 |
| `↑ / ↓` | 输入框边界处回溯输入历史；菜单打开时导航菜单 |
| `Esc` | 关闭当前浮层 |

删除不提供单键快捷键，避免误操作。

## 7. 模型与资源归属

每条对话保存独立的模型和工作区资源配置：

- 新对话的模型模式默认为 `follow-default`。
- LLM 默认模型变化时，所有 `follow-default` 对话在下次激活时使用新默认值。
- 用户在某条对话中手动选择模型后，该对话变为 `pinned`，不再被默认模型变化覆盖。
- 用户可以在模型菜单中选择“恢复跟随默认”。
- 附加的工作区资源、工具轨迹和待审批操作均属于具体对话，切换对话不能串用。

## 8. 数据模型建议

```ts
interface ChatConversation {
  id: string
  title: string
  titleSource: 'automatic' | 'manual'
  createdAt: number
  updatedAt: number
  lastMessageAt: number | null
  deletedAt: number | null
  modelSelection: {
    mode: 'follow-default' | 'pinned'
    providerId: string | null
    modelId: string | null
  }
  resourceWorkspaceIds: string[]
  draft: string
  scrollTop: number
  messages: Message[]
  toolTraces: ChatToolTraceEntry[]
}
```

运行时状态与持久数据分离：`isStreaming`、abort handle、pending content、agent session 和 approval 不直接写入持久文件，只通过 conversation id 建立关联。

## 9. 持久化与架构建议

第一版不引入数据库依赖，使用主进程文件仓库：

```text
userData/janus-chat/
├─ index.json
└─ conversations/
   ├─ <conversation-id>.json
   └─ ...
```

- `index.json` 只保存排序、当前对话 id 和轻量元数据。
- 每条对话独立文件，避免修改一条消息时重写全部对话。
- 使用临时文件 + rename 进行原子写入。
- 只在用户消息提交、助手消息完成、标题/资源/模型变化时持久化；流式 delta 不逐字写盘。
- 草稿采用 300–500ms 防抖保存。
- Renderer 通过受限 IPC 调用 `list/get/create/update/delete/restore`，不直接访问文件系统。

现有 `useJanusChat` 应演进为 `useJanusConversations` 控制器，并将单一 messages/state 拆为 `activeConversationId + conversations + runtimeByConversationId`。

## 10. 迁移策略

当前版本没有持久化对话记录，升级时采用无损内存迁移：

1. 应用运行中升级控制器时，把现有消息包装为一条 `titleSource: automatic` 的对话。
2. 第一次持久化成功后再切换到新仓库状态。
3. 资源偏好从现有全局状态迁入该对话。
4. 如果迁移失败，继续保留当前内存消息并提示“对话保存失败”，不得清空界面。

## 11. 异常与边界状态

- 存储文件损坏：隔离损坏文件，列表显示“无法读取的对话”，允许导出原始文件或删除。
- 模型被删除：打开对话时标记“原模型不可用”，回退当前默认模型，但不静默改写 pinned 配置。
- 工作区被删除：保留对话，移除失效资源并显示一次性说明。
- 删除最后一条对话：自动创建新空对话。
- 搜索无结果：显示“没有匹配的对话”，保留新建入口。
- 多窗口同时写入：主进程仓库串行化写操作，以 revision 检测过期更新。

## 12. 分阶段落地建议

### Phase 1：可用闭环

- 新建、切换、重命名、软删除和撤销。
- 文件持久化与启动恢复。
- Island/嵌入窗口共享当前对话。
- 每对话草稿、模型与工作区资源。
- 单活动流；生成期间切换需停止确认。

### Phase 2：连续使用

- 搜索与时间分组。
- 多对话后台生成。
- 失败状态、恢复和运行资源隔离。
- 已删除对话恢复入口。

### Phase 3：高级管理（按需求评估）

- 置顶、归档、批量删除。
- 对话导出。
- 文件夹或标签。
- 跨设备同步。

## 13. 验收标准

- 新建、切换和删除对话后，Island 与嵌入窗口始终显示同一当前对话。
- 应用重启后恢复对话列表、当前对话、消息、草稿、模型和资源。
- 删除可在 5 秒内撤销；删除当前或最后一条对话不会出现空白死状态。
- 手动选择模型的对话不被默认模型变化覆盖；跟随默认的对话能正确更新。
- 任一对话的消息、工具轨迹和资源不会进入另一条对话。
- 100 条对话、每条 200 条消息时，打开列表和切换对话没有明显阻塞。
- 所有对话管理操作均能仅通过键盘完成，危险删除操作不会由单键直接触发。

## 14. 推荐结论

建议先落地 Phase 1，并采用“覆盖式管理面板 + 主进程文件仓库 + 每对话独立运行状态”的组合。它与当前 Island 的紧凑结构兼容，改造路径明确，也避免在需求尚未验证时提前引入数据库、文件夹和云同步等高成本能力。
