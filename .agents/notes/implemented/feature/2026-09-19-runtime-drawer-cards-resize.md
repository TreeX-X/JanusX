# Agent Note: Runtime drawer cards and drag height

Status: implemented

## Problem

The bottom drawer in `TerminalArea.tsx` lists terminal runtime telemetry as one table row per terminal: provider, model chip, a context bar with its label, and an age column packed into a four-column grid. The row only fits when the terminal area is wide, and the context label and the bar fight for the same column, so the line the user most wants to read is the one that truncates first. The drawer height is fixed per view and the list caps at 141px, so a workspace with more than three terminals scrolls inside a strip too short to compare them, and no gesture lets the reader trade pane height for drawer height.

## Decision

The runtime view renders each terminal as a card in an auto-filling grid with a 220px column floor, so the number of columns follows the drawer width instead of a fixed column list. A card stacks provider with status dot and age on the first line, the model chip on the second, then the context label with its percentage above a full-width usage bar; the active terminal card carries the accent border, a neutral background one step lighter than the other cards, and `aria-current`; the accent never fills the card because a tinted block reads as a warning state rather than a selection. The card keeps the `ContextUsagePopover` hover preview on its usage block, and clicking a card still activates that terminal. The list fills the drawer and scrolls only when the cards exceed it.

The drawer height is user-adjustable per view. `quick-note-behavior.ts` owns the model: a 28px collapsed height, a 120px floor, a 160px pane reserve, the 210px and 380px defaults per view, and `clampDrawerHeight` which rounds and clamps between the floor and a caller-supplied ceiling. `getDrawerHeight` takes an optional per-view override map and falls back to the defaults, so the drawer opens at the same height as before until the user drags. `TerminalArea.tsx` keeps the override map in component state, renders a 7px `term-drawer-resize` separator across the drawer's top edge when it is open, and drives it with pointer capture the same way the right dock drives its width handle; the ceiling is the terminal area's height minus the pane reserve, measured when the drag starts. Arrow keys move the handle by 16px and Home and End jump to the floor and ceiling. Every height change refits the focused terminal, and `CLITerminal` re-takes DOM focus for its helper textarea on each refit, so the handle re-focuses itself when a blur lands on that textarea within 250ms of a resize keystroke; without this the second arrow press types into the terminal. A CSS `max-height` of the area minus the pane reserve sits on the drawer container, so a window that shrinks after a drag keeps the pane reserve without a resize observer, and the height transition is suppressed while a drag is live so the drawer tracks the pointer.

## Alternatives considered

- Persist the drawer height in a store like the right dock width — strongest case is that a chosen height survives restarts. The driver that rules it out is that the drawer is closed on every launch and the two views want different heights, so a persisted value needs a schema and migration for a preference the user re-establishes with one drag; component state keeps the change local and reversible, and persistence can be added when the launch-closed default changes.
- Keep rows and only add the drag handle — strongest case is a smaller diff with no visual change. The driver that rules it out is that a taller drawer makes the row layout worse, since the rows grow no wider and the empty space below them carries nothing.
- Fixed two-column card grid — strongest case is a stable layout that never reflows. The driver that rules it out is that the terminal area width ranges from a narrow split pane to a full window, and two fixed columns either truncate model names at the narrow end or leave half the width empty at the wide end.
- Do nothing / reuse — staying put keeps the row list and the fixed heights. The cost is the truncated context line and the 141px cap that hides most terminals in busy workspaces.

## Consequences

- **Gains**: Each terminal's context usage reads as a unit with its own bar and percentage, and the grid shows as many cards as the width allows. The user can pull the drawer up to compare all terminals and push it down to give the panes room, with a keyboard path on the handle.
- **Costs and limits**: The chosen height lives in component state and is lost on reload, and the handle is not present while the drawer is collapsed, so collapse and expand keep the default until the user drags again. The pane reserve of 160px is a constant and not derived from the terminal's minimum rows, so a very short window can still leave the terminal cramped. The note view shares the handle and the clamp but keeps its own default height. Cards render inside the drawer only, so the sidebar and tab strip keep their existing status forms, owned by [terminal status ring](./2026-09-19-terminal-status-ring.md) and [terminal status display](./2026-09-12-terminal-status-display.md).
