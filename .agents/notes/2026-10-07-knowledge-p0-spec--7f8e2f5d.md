# 工程知识重构 P0：范围、契约、模块与验收规格

## Problem

本规格将[持续讨论](./2026-10-07-knowledge-pipeline-reconstruction--c459c727.md)收敛为工程知识实施边界。用户已启动 P0；个人画像/记忆机制在 P10 最后实施。当前主要问题是恢复记录自增、同文证据身份冲突、全历史重复提取、整批失败阻断产出，以及知识卡片晦涩。具体现场数量与来源见持续讨论，不将历史任务数量当成独立知识或当日成功率。

本文件是待整体确认的规格，不表示 P1 已开始，也不将设计指标写成已测性能。用户在 P0 明确选择旧工程内容“不备份，全部进行删除”；切换方案据此采用清空重建，不迁移、不备份、不重新提取旧工程材料。本次只设计，尚未执行删除。个人数据仍按提问范围保留至 P10，外部原始 CLI 会话文件不属于知识库存储清理对象。

### 代码与数据事实

检查基线为 `841b012739b0c3ac4473f08863fe3ed04031a610`；同时存在其他工作中的未提交变更，后续实施先核对最新代码。现有[记忆与知识模块声明](./2026-10-03-module-memory--c1c04881.md)拥有此范围，当前不新增重复模块声明或把规划目录写成已实现模块。

- `src/main/knowledge` 当前有 81 个文件。observation-service、review-service、processing-queue、recall-service、extract-service 等文件分别集中多类责任；P0 统计行数仅作拆分信号，不设机械行数门槛。
- 注册入口仍同时装配确定性处理、旧 LLM/精炼以及自动化服务。删除旧规则文件前必须处理注册器、设置、IPC 和个人域调用方。
- 工程与个人共用 observations、facts、候选、审计和若干屏障/恢复服务，不能按整个 knowledge 目录删除。默认知识根由 constants 解析到 JanusX，而配置使用 Electron userData；本机 JanusX-Dev 有配置但无独立 knowledge 目录，测试必须显式注入隔离根。
- 候选与正式事实当前存于两个文件，事实和 Wiki 发布已有恢复日志及审计提交点。新模块化必须保留原子发布和恢复能力，不能把多文件先后写误称为事务。
- 条目、Wiki 和 IPC 的核心契约归属本仓库 shared；@janus-agent 包在此范围主要提供通用脱敏、运行/对话接口。当前未发现必须修改相邻仓库的既定要求；若实施发现需要改变共享端口，另记具体依赖，不修改 node_modules 代替源码变更。
- 当前 JEV 按 support、consistent、coverage 返回分值；候选自身作为唯一 required 项不能证明本批证据没有漏提。条目支持性和批次覆盖要分开设计。

## Expected behavior

### 流程与对象

主流程为：程序采集 → 证据就绪 → 小批积累与上下文组织 → LLM 提取 → 候选知识条目 → 人工或自动审核 → 已确认条目 → Wiki 草稿 → 审核发布。没有提取模型时正常采集，并显示等待配置；不能回退为旧关键词知识提取，也不能将未处理标记为成功。

建议已确认条目持续保存，生成 Wiki 不删除条目。Wiki 是阅读投影与独立版本文档，依据条目及受支持的 Note 引用生成。沿用现有左侧入口，不在 P0 改默认页签；条目可从现有知识库列表阅读，并从 Wiki 查看引用。此保留和导航建议随最终 Ready Summary 一并确认。

### 数据契约草案

共用基础字段包含 schemaVersion、id、domain、明确 owner、createdAt/updatedAt；以下对象各自有业务结构，不将它们塞进一个带大量可选字段的万能对象。字段命名允许实现阶段机械调整，身份、状态和验证语义不得悄悄改变。

| 对象 | 必需信息 | 责任与身份约束 |
| --- | --- | --- |
| EvidenceRecord | engine、sessionId、nativeMessageId、turnId、speaker、authority、sourceTime、observedAt、正文/分块引用、contentHash、来源定位 | 身份由领域/工程/引擎/会话/原始消息确定；来源未知明确标记，不从正文猜角色；同文不同消息不自动等价 |
| CaptureTurn | turnId、原始开始/结束事件、消息引用、正文完整状态、补读原因与期限 | Hook 是触发信号，不是新的知识正文；恢复只更新同一回合，状态事件不再成为提取输入 |
| ExtractionBatch | batchId、输入证据 ID+版本、确定的回合边界、contextRefs、configRevision、checkpoint、覆盖结果 | ID 基于固定输入清单和提取协议；配置切换不永久卡住旧 pending，也不把旧成功全部自动重算 |
| KnowledgeEntry | entryId、kind、title、body、conditions、concepts、evidenceRefs、revision、contentHash、状态、替代关系 | 一个可独立理解/核验的知识点，例外不拆散；候选到确认保持对象身份，语义变化新 revision |
| ReviewRecord | entry/page ID+revision+hash、来源快照、依赖版本、method、policyRevision、结论、分项依据、时间 | 人工/模型共享提交边界；结果不得授权另一版本，历史结果不可冒充当前状态 |
| WikiPage/WikiDraft | pageId、workspaceId、slug、revision、正文、sourceEntryRefs、sourceNoteRefs、relations、状态和来源新鲜度 | 草稿和正式页面分离；引用绑定 ID+版本+hash，发布正文、关系、历史及索引一致提交 |
| ProcessingJob | jobId、对象版本、stage、status、attempts、startedAt、finishedAt、nextRunAt、reason、调用量 | 运行任务与知识对象分离，历史重试不增加当前待办，调度器不存第二份知识正文 |

引用建议使用 evidenceId、sourceRevision/contentHash、明确文本范围以及原文片段。范围单位由协议固定，不能混用 UTF-8 字节与 JavaScript 字符下标；P1 先验证各采集适配器。模型输出的引用需由宿主定位原文并复核，脱敏后不可逆的信息不得回填。摘要不取代原始依据。

状态建议采用三个互相独立的维度：条目 `candidate/confirmed/rejected/superseded/archived`，任务 `pending/running/waiting-evidence/waiting-provider/retry-scheduled/needs-human/succeeded/failed/cancelled`，批次结果 `complete/partial/no-knowledge`。具体存储可使用更少字段，但不得再用单一 needs-review 同时表示没正文、模型错误和用户要决定的内容。

候选正文修改使原审核失效；来源内容变化使依赖审核失效；新增无关聊天不改变所有旧候选身份。当前版本仍有足够有效证据时可重审，新旧冲突明确分流。拒绝后的相同输入不自行复生，新证据可形成新的可解释版本。

### 采集与上下文

保留现有已支持引擎的 Hook/会话适配入口，先覆盖 Codex、Claude、OpenCode、Pi 和 Janus 现有路径，不扩展新 CLI。外部 Hook、Janus 对话、现有执行/维护证据入口统一为来源适配器；完整正文和工具结果可作证据，工具包装不直接成为条目。保留手动提交及 Note → Wiki 的既有功能，适配统一审核和引用，不另建第二条自动提取管线。

证据按回合即时持久化，已结束且完整的回合进入批次。失败回合可保存有效已完成部分，但失败本身不是“修复成功”的依据；正文仍不完整的回合留在恢复队列。不能因为需要完整上下文而永久等待整个会话关闭。

每批输入分为新增证据、必要历史、已有相关知识。必要历史优先包含目标、有效约束、指代所指方案和纠正；已有候选可帮助识别重复，但不能作为已确认事实支撑。上下文不足则返回结构化补取请求，由宿主按相同工程和来源限制读取，不能让提取模型任意执行工具或扫描整个文件系统。

首轮调优基线建议：累计 3 个完整回合、就绪输入达约 8K token、会话空闲 60 秒或最老就绪证据等待 180 秒时触发；任一条件可触发，持续输入不重置最老计时。最多 24K 输入 token（包含历史及相关知识）且受模型实际上下文扣除系统/输出预算后的上限约束；小模型按更小预算分块。超长回合按语义段落和来源范围分片，不能直接静默截断。

上述数字是待测初始参数，不是用户承诺或所有提供方的硬编码。180 秒只约束进入就绪调度，不代表提供方必在 180 秒内生成结果；排队与模型耗时分开记录。补取最多两轮、局部修复最多两轮作为初始预算，耗尽后保留可恢复结果与原因，不能无限循环。

### 提取与审核策略

提取输出包括候选和批次覆盖记录；允许有依据的空结果。标题是阅读摘要，正文保存完整结论及条件，不能把报告“完成了 80 项测试”作为长期知识。对可独立验证的候选逐项保存及审核，跨条目依赖或矛盾一起判定；批次仍有覆盖缺口时显示 partial，不能因为部分条目入库就声称提取完成。

审核分为宿主确定性验证与模型语义验证。宿主检查来源身份/作用域/原文绑定/版本/撤回/配置；JEV 或现有受支持审核提供方检查证据支持、条件和冲突。审核只能批准当前快照；提交锁内再复查读取集合。

建议分流：有效新条目通过自动审核可入库；含冲突或替代已确认结论的条目交人工决定；不确定语义交人工；引用错位先局部修复；正文待补留恢复；超时/429 使用有界退避；明确不支持的候选标为未采纳并保留原因。人工也不能批准不存在的引用或错误工程归属，需要先修正内容/来源。用户可主动将自动排队项转人工处理，但在途自动结果必须失效，不能发生两次提交。

JEV coverage 针对独立列出的关键条件和来源结论检查，而非重复候选正文自证。批次漏提评估由提取/覆盖检查与独立测试标注承担，不将“每条都正确”视为“没有漏提”。阈值先保留可配置能力，默认值沿用当前配置后由校准集验证；是否调低由证据决定。分数仅标记实际分项得分，不显示成审核正确率。

### 存储、发布与多进程

建议保留文件存储与现有可恢复提交思路，由 store 模块隔离物理布局；新增工程版本目录分为 evidence、turns、batches、entries、reviews、jobs、wiki、audit 和派生 indexes。具体文件分片与索引先用存储接口屏蔽，不在没有基准前引入新数据库。

发布需要单一写入所有者与可恢复事务：记录写入意图，验证 expectedRevision/读取集合，提交领域对象和审计标记，最后完成清理。读者不得读到部分发布状态。进程内 SerialQueue 不足以保护多进程共享数据根；P1/P8 需要目录级所有权或进程间写锁，外部 MCP 保持只读，多实例争用要显式显示，不能悄悄覆盖。

已确认条目与 Wiki 发布分别有事务；批次多个独立候选不强求一次全局事务。旧个人存储在 P10 前独立保留，工程不再写旧个人/工程混合格式，读取适配不得将旧工程内容重新注入新库。图库索引和全文索引均为可重建派生数据。

### UI、设置与运行状态

卡片、详情、审核操作和状态在工作台与助手入口复用。保留左侧 navButton/navActive、共享 TabStrip 及主题体系；改造内容组织与动作，不改全局导航风格。现有 Library 可承接已确认条目，Wiki 页保留来源跳转，审核入口区分自动处理中、需人工判断和系统受阻。候选无法成为常规正式召回结果。

工程设置有效变更自动持久化：开关和选择器立即提交；文本输入验证通过后短防抖提交，失焦刷新有效草稿，页面关闭仍有保存状态提示；非法地址不写坏有效配置。所有保存携带 revision，乱序响应不覆盖最新值。UI 无保存按钮；失败明确提示，不能显示为已生效。

建议模型配置变更只影响未启动及明确重试的任务，在途任务记录原配置版本；禁用功能立即取消在途并禁止提交。审核阈值变化使尚未提交的审核结果重新验证，不批量重审所有已确认历史；对现有待审提供显式重新评估动作。旧配置从有模型变成无模型时，证据保留、任务等待配置，不降级为自动确认。

运行摘要至少区分：已就绪回合数、积累中批次、当前运行阶段、可执行待办、系统受阻、人工待审、最近实际入库时间。历史尝试和当前任务不能相加。模型调用开始/完成、输入量、延迟、产出和最终入库分别计量，状态查询不触发任务也不重新扫描/规划全部历史。

## Scope

### 本轮范围及延后项

P1～P9 覆盖工程采集到 Wiki 的全链路、旧工程格式退出、设置和 UI、查询/MCP/助手消费、旧测试更新及真实能力验证。保留现有 Note-Wiki 来源、新鲜度、人工编辑所有权及 Wiki 页间关系约束。没有额外的通用自主 Agent、新 CLI 集成、全应用主题重做或大型向量数据库迁移。

P10 才实施个人画像/记忆新机制、显式记住即时确认、自然记忆自动审核及个人旧格式迁移。此前保护个人现有功能与数据，工程删除不得破坏个人引用的共用证据。人设、Harness 和其他工作中的配置/样式修改不属于本次写入范围。

### 建议模块目录及依赖

以下是拟建结构，不宣称当前已存在。优先在既有 knowledge 边界内部重组，避免每层创建无意义的 service/repository/manager 三件套。

```text
src/shared/knowledge/
  evidence.ts  entry.ts  review.ts  wiki.ts  processing.ts  settings.ts
src/main/knowledge/
  capture/       # Hook/Janus 来源、回合归属、补读与去重
  evidence/      # 原文定位、完整性、撤回与有界读取
  batching/      # 回合积累、输入清单、上下文选择与补取
  processing/    # 任务状态、调度预算、重试及检查点
  extraction/    # 提取契约、整理、覆盖、引用修复
  review/        # 策略、人工/自动入口、快照校验
  entries/       # 条目生命周期、去重/替代、发布
  wiki/          # 主题生成、来源绑定、发布及新鲜度
  providers/     # 生成/JEV 适配及现有本地模型接入
  store/         # 存储接口、版本布局、锁、恢复事务
  query/         # 工作台投影、检索、召回、运行摘要
  runtime.ts     # 组合根，仅装配，不包含各阶段业务
src/renderer/src/components/knowledge/
  cards/  entries/  review/  processing/  wiki/  settings/
```

shared 契约不依赖宿主/renderer；IPC、MCP 和页面调用应用接口；processing 调用阶段执行接口，不导入提示词或渲染组件；provider 不持有知识发布权限；entries/wiki 通过 store 提交。跨目录引用只通过指定公共入口，内部工具保持就近，禁止循环依赖。暂留的个人实现与旧共享 helper 明确隔离，不因重命名工程文件提前改个人机制。

### 旧数据清空方案（用户已选择）

切换时删除 JanusX 知识存储内的旧工程 observations、只被工程引用的 blobs、工程候选/正式条目、Wiki 正文/草稿/历史、旧工程图边/索引、工程处理与恢复任务、工程审计及派生缓存，不制作备份，不迁移或从旧材料重新提取。保留个人资料及其所需证据、账号凭据与设置、项目源码、`.agents/notes` 和外部 CLI 原始会话文件；这些不是旧工程知识条目。

实施前生成按归属计算的删除对象清单与共享引用计数，只输出身份/数量/路径，不复制正文作为隐性备份。共享文件按记录过滤，工程独占文件才整文件删除；工程和个人共用 blob 在个人仍引用时保留。无法确定归属的记录先报告，不猜测删除个人内容。切换时核对知识根的绝对路径，锁定写入，记录切换时点/每会话起始水位，阻止恢复任务、历史扫描和旧进程把已清空的工程内容写回来。

### 初步质量门槛

固定人工标注测试集上建议：提取精确率至少 95%、加权召回率至少 90%、关键否定/条件/数字/范围丢失为 0；高风险负样本错误自动批准为 0；明确可通过样本自动通过率至少 80%，避免全部转人工“实现零误批”。这是发布门槛建议，不是对真实世界的统计保证。各指标按场景族单独展示，校准子集和留出集分开；关键失败逐项报告，不只给总体均分。
