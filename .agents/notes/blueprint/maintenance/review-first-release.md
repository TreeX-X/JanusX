# 首版重点 Note 审核：类型、代码依据与反馈闭环

## Intent

用户确认首版先审核重点文件，逐步推进，优先把整条链路和记录做好；主要寻找矛盾、遗漏和不足。用户进一步询问能否结合工程代码核对 Note，以及为决策合理性提供参考。本篇维护首版范围与具体设计建议，总体权限、模型分工和反馈交接由[审核总览](note-content-review.md)维护，排期由[交付计划](../evolution-roadmap.md)维护。

已确认首版语义审核覆盖 decision、module、requirement 三类，检查矛盾、遗漏和不足；Agent 读取必要上下文后分析并发布，JEV 按配置随后补充数字评分，无 JEV 时直接提供建议，外部决定修改。Git 差异用于确认变化及辅助审核，首版不做差异过滤。自动审核默认关闭，累计全部 Git 提交、默认 N=5，启动语义审核前须配置生成式 LLM 并在设置页检测；手动审核保留。取证、结果校验与实测样例已实现，质量限制见下方实际验证。

## 首版类型与覆盖范围（已确认）

| 优先目标 | 首版检查内容 | 对照依据与状态边界 |
| --- | --- | --- |
| module：模块说明 | 已有职责、接口、关键行为和限制是否与证据相符；模块之间是否互相矛盾 | 当前实现片段、接口与相关模块；planned 部分不按已实现要求核对，partial 需逐条区分规划和现状 |
| decision：决策 | 选项是否符合明确需求；原因和前提是否有依据；条件变化后是否需要复议；已实施陈述是否与代码相符 | 关联需求、有效约束、明确替代方案、必要实现证据；accepted 尚未实施不能直接判错，历史决定按当时条件理解 |
| requirement：需求 | 要求是否相互冲突，条件和可判定标准是否缺失；已声称交付的验收项是否有实现依据 | 原始有效要求、关联决定和验收材料；代码不满足未交付要求时属于实现差距，不据此改写需求 |

首版覆盖当前项目内所有 module、decision、requirement Note，不开发指定模块/文件范围、排除清单或范围继承配置。新增 Note 和所有子模块按同一类型规则自动纳入；草稿、已生效、历史和归档状态均不排除。建议以一个真实模块内的三类 Note 建立验证样例；样例选择不缩减产品覆盖范围。

普通 note、idea 和 task 的专项语义检查后置，当前可独立执行结构检查而无需模型。[harness-note 结构审核](note-content-review.md#harness-note-结构审核)覆盖全部正式 Note 类型，由程序复用固定标准检查，诊断进入审核视图并支持文件定位和修复复查；目标结构错误或检查未完成时不启动语义生成。它们仍可作为明确关联的证据读取，不因被引用就加入语义目标集合。Task 既有验收和独立评审义务保持原契约。

## 审核目标的确定方式（已确认）

用户已确认“点击卡片 → 左侧 Note 预览 → 审核当前 Note”，原文与可折叠建议同屏，建议按概要/展开依据分层展示并可定位原文。手动审核不受 N 次提交、Git 是否有差异或自动开关限制，但须配置生成式 LLM。审核建议只能由左侧手动与 Git 自动审核生成；右侧通过原生 MCP 读取已有建议并在授权内调整，不提供审核或建议生成触发。详细展示和接入边界由[审核总览](note-content-review.md#蓝图与右侧对话)维护；不开发自定义范围与批量勾选。

自动审核启用后，项目内全部三类 Note 都属于覆盖范围。本轮实际目标由 Git 的变化文件确定；新建文件可由 Git 新增记录识别，新子模块中的三类 Note 同样参与，无需用户再次配置。自动触发仍要求这些变化已进入提交；覆盖全项目不等于每轮向模型提交所有 Note，也不代表开启时已审核存量内容。

审核目标与取证材料分别记录：审核一篇决策可能读取相关需求和代码，但读取材料不等于将它们全部加入本轮语义审核目标。已记录的依赖变化可以让报告过时；依赖变化本身不独立启动语义审核。尚未建立依赖映射的代码变化无法保证自动找到所有受影响 Note，应报告此覆盖限制。

报告记录实际审核目标与读取材料，不增加逐项确认或持久化范围偏好。首版语义审核只按三类类型确定覆盖范围，也不对 Git 差异做时间、格式等过滤；生命周期影响内容解释，不影响是否纳入。草稿不能按已实施方案核对，历史决定应按当时条件理解；缺少对应历史依据时说明材料不足，不强行用当前代码否定旧决定。Q13 已确认，自动节奏与计数异常由[审核总览](note-content-review.md)和交付计划 Q9 维护。

### 用 Git 确认变化

用户已确认普通自动审核累计全部 Git 提交，包括仅修改代码的提交；N 可设置，默认 5，自动审核默认关闭。启用后达到 N 次先检查 Note 差异，没有 Note 修改就不启动后续自动化。已确认普通周期与合并专项审核共用一个自动审核总开关。关闭时仍检测变化、标记旧建议过时，保留当前待处理建议，不自动调用模型；开启且模型配置满足前置条件时，合并完成后专项检查不等 N，蓝图内部发现无通知合并也执行同一流程。蓝图整理材料与审核、获授权 Agent 修改正文；内部检测及恢复细节由[审核总览](note-content-review.md#合并完成后的专项检查)维护，尚待细化。首版自动候选为“当前项目内，自上次差异检查基准以来由 Git 检出变化的三类 Note”，包含新增文件及所有子模块，不只查看最后一次提交，也不因仅代码变化而自动扩展目标。Git 负责发现变化和定位版本；hash 记录原始输入版本及重复任务身份，不通过忽略字段或内容归一化筛掉真实变化。工作区 clean 不代表已经审核。

差异检查成功后推进检测基准，包括无变化的轮次；各目标的审核完成版本另记。模型失败、取消及未完成目标保留状态，不随计数清零而丢失，也不在无差异轮次隐式重试。首次启用已确认以启用时当前提交建立基准、从 0 计数，不回放项目既有提交；存量 Note 仍可浏览和单篇手动审核，未检查不等于通过。已有有效检查点的重启/升级不重置基准。用户已确认关闭 Janus 时暂停审核，重开且自动审核仍开启时补算并合并检查一次，未达 N 继续累计，无 Note 差异不调用模型。已确认的初始基准由[审核总览](note-content-review.md#首次启用与已有提交)维护；分支分别计数、切换不计提交、普通合并计一次、普通单父提交计一次及快进口径已明确；压缩合并等特殊来源识别暂缓，有限重试已确认：临时异常最多自动重试一次，配置错误不重试，仍失败由左侧手动恢复；历史改写等特殊补检暂缓，等待参数由实施确定。

Git status 仍可识别工作区、暂存和未被忽略的新文件，供界面及手动审核使用。用户已确认审核必须读取必要上下文；Git diff 只用于确认变化文件和审核时辅助判断，不限制审核只读修改行，也不等同于矛盾证据。目标原文、相关约束和必要代码按实际问题取证。相关代码/需求变化可以使旧报告过时；独立依赖触发属于后续可选扩展。

首版明确不做差异过滤：Note 文件内仅更新时间、元数据、空白/格式或布局字段变化，也不先判断重要性后跳过。画布独立配置等非目标 Note 文件不因本规则成为审核目标。移动/重命名保留 Git 变更记录并依据 Note UUID 延续身份；确认目标删除后，由[建议管理模块](suggestions/module.md)自动清理其建议与当前报告，不等待提交阈值或人工处理；这表示目标退出，不表示问题修复。移动、恢复、来源失败及依赖删除同样由该模块统一处理。审核报告是派生数据，不属于这三类原始 Note。

Git 提交只包含已跟踪且提交的内容。未提交/未跟踪 Note 可显示为待提交变化并手动审核；被 Git 忽略的 Note 或无 Git 项目沿用文件扫描与 hash 检测，不强制初始化仓库。Git 变化集合与三类类型共同确定本轮目标，不提供指定范围配置。提交后异步审核、快照一致性和补查机制见[自动化审核方案](note-content-review.md#自动化审核的定位)。

## 三类问题的判定边界

| 类别 | 可以提出什么 | 不能据此推断 |
| --- | --- | --- |
| 矛盾 | 两条有效陈述在同一条件下互斥，或现状陈述与有依据的实现不一致；引用两侧原文及条件 | 不匹配不自动意味着 Note 错，可能是代码偏离要求、版本不同或功能尚未实施 |
| 遗漏 | 有明确来源要求记录/覆盖某个条件或行为，但目标文档遗漏；指出预期项与来源 | 不能从“没有读到/搜索没命中”推出全工程不存在，也不要求模块文档罗列每个实现细节 |
| 不足 | 说明缺少适用前提、决策依据、重要限制或可判定标准，导致当前问题无法明确解释 | 本次没有取得证据应单列“材料不足/未覆盖”，不能一律判成文档内容缺陷 |

首版不包含纯文风润色、泛泛的最佳实践打分或“所有可能改进”的开放式巡检。需求的规范性与代码的现实状态分别保留，审核器不把任意现有代码提升为应当遵循的产品要求。

## 工程代码怎样成为 JEV 的依据

技术上可以将代码片段、Note 原文和明确检查问题一起作为 JEV 的输入。当前适配接受序列化材料并返回按问项评分，具备传入代码文本的基础；这不证明其在本项目语言、框架和长调用链上的准确率。首版需要专门样例验证，不能把 JEV 当作编译器、静态分析器或测试运行器。

取证优先从 Note 的 codeRefs、明确文件/符号引用和模块入口开始。程序定位并读取实际源码，Agent 识别目标陈述、必要依赖和适用条件；按需要补充调用方、配置来源、分支与已有测试证据。没有足够定位信息时可做有界搜索并记录覆盖范围；跨仓源码不可用、动态行为无法静态判定或模型上下文窗口不足时报告未覆盖。

证据固定到本次明确选择的版本：提交触发时，Note 和同仓代码从同一目标提交读取；手动审核当前修改时，固定实际读取的工作区内容并保存 hash，读取期间变化需检测并重试或报告未取得一致快照。两种模式均保存路径/符号/片段位置和采集范围；不能将提交版 Note 与随后修改的工作区代码混用，仅记录提交号也不能代表未提交修改。跨仓依据分别固定真实版本并标明兼容性限制。审核输入保留原始片段；Agent 生成的摘要不能成为证明摘要本身正确的唯一依据。

每个问项应足够明确，例如“在指定条件下，这段实现是否支持 Note 声称的失败重试行为”或“该决策是否满足需求中明确要求的多进程写入约束”。避免直接问“整个模块是否正确”“这个方案是否合理”。对可由程序精确核对的身份、引用和结构问题优先使用程序检查。

JEV 返回针对输入问项的信号；程序保留原始结果及定位，生成式 Agent 再结合原文分析。没有清晰依据时只提出待复核提示。读到了测试代码只能证明存在相关测试断言；只有真实执行结果才能作为测试通过证据，静态片段也不能证明运行时所有路径都正确。

示例（非本项目事实）：模块 Note 声称某调用失败后最多重试三次，已定位的当前执行路径配置为不重试。反馈展示 Note 陈述、有效配置来源与该路径的范围，并标为行为不匹配；后续由维护 Agent 对照需求判断应修正文档、修改代码还是补充适用条件。不能自动把 Note 改成“不重试”来消除提示。

## 决策“合理性”的首版含义

首版核验的是能被明确约束的部分：选择是否违反现行需求，原因中的事实是否成立，关键前提是否变化，重要限制是否漏写，以及“已经实施”的陈述是否得到代码/验证支持。

例如单进程条件下采用文件存储的决定，遇到多进程写入要求后需要重新核对并发前提。这提供复议依据，不证明原决定当时不合理，也不证明某个替代方案必然更优。性能优劣、维护成本、长期架构取舍等开放判断由生成式 Agent 提供参考并由外部决定；JEV 不能仅凭一个总体评分裁定。

## Agent 先分析与可选 JEV 评分

Agent 读取当前原文与代码、生成可定位的问题和建议，经来源、引用、覆盖与版本校验后先发布报告。启用 JEV 时后台对每条问题依据给出数字，补充到同一报告与来源版本；无需第二次生成调用，也不等待 JEV 再发布。JEV 失败显示评分暂不可用，无建议时不调用评分。高低分均不改变建议集合，不决定修复是否通过，完整复审结果替换旧集合的规则由[建议管理](suggestions/module.md#修复后的整批替换)维护。

每个数字保留问项含义、模型与输入出处。对“问题是否有依据”和“原 Note 是否一致”的问项必须区分方向；不能把评分解释为全文正确率或修改命令。当前 UI 只显示原始数值和可用性，旧 supported/disputed/uncertain 值仅作存储兼容。超时、取消及迟到结果处理见[审核总览](note-content-review.md#jev-辅助评分)。

无 JEV 的建议路径仍须有可用的生成式 LLM。已确认审核模型单独配置，建议生成模型从已设置的生成式模型中选择；手动、普通周期及合并审核共用同一组配置。设置页采用已确认的同页三分区，设置修改即生效，不提供保存/应用控件；必须自动检测必要配置与可用性，未启用 JEV 和启用后失效分别表达；右侧对话默认模型及后续指令切换不改变审核配置。自动审核默认关闭，配置完成或检测通过也不自动打开。手动入口沿用同一模型前置条件，具体检测和引导由[审核总览](note-content-review.md#设置与-llm-配置前置条件)维护。JEV 配置与 MCP 连接分别管理，未安装某个 MCP 客户端不等于未配置 JEV。

建议按概要、证据与数字评分分层展示，不按 JEV 阈值分组或排序。流程认可不增加强制采纳或发布关口；自动默认值、基本节奏与全项目三类覆盖已确认。Q12 审核部分仅在有意见时提示，不设计多状态审核灯；原灯位已确认复用为待处理意见提示；同一 MCP 显式清理当前建议、不保留历史的规则已确认，由[建议管理模块](suggestions/module.md)维护，字段由实施确定。原状态文字对新 Note 元数据的适配见[状态显示](../navigation/note-status-display.md)，不受审核触发节奏控制。

## 最小闭环与可扩展边界

1. 左侧手动审核当前一篇 Note；自动审核由 Git 变化确定三类目标，固定版本、类型与生命周期。开发可选少量样例验证，不提供模块范围选择或批量勾选功能。
2. 组织目标原文、相关约束及必要代码；Agent 分析并提出可定位的问题/候选建议，记录已读与未覆盖材料。
3. 程序检查确定性约束并发布版本绑定的完整或不足报告，绑定规则版本、生成模型和实际输入。
4. 按配置后台补充 JEV 数字评分；评分不改写已发布的问题和结论。每项记录问题身份、类别、目标陈述、依据、条件、来源版本、覆盖范围及建议来源，错误与材料不足分别呈现。
5. 用户或外部 Agent 通过界面、当前读取入口或 MCP 获取反馈，自行决定修改、不采纳或暂缓；沿用已有权限维护 Note/代码。
6. 来源改变后由建议管理模块标明尚未完成的当前建议可能过时，仍存在的目标由手动或 Git 自动审核核对；目标删除则自动清理，不再审核已删除正文；合并专项与普通周期规则保持。Agent 经同一 MCP 显式清理已处理/不采纳条目，不留历史；失败、漏审或普通内容修改不误清理。被完整替代的报告删除，当前所需来源与版本仍随待办保存。

类型与生命周期只决定检查项选择，证据组织、核验适配、报告和对外交接复用同一能力。首版可用少量规则函数或配置维护重点检查项，不预先建设通用规则引擎。后续新增类型应沿用原有来源与反馈语义，但仍需针对该类型补充样例和质量验证，不能因接口可复用就宣称扩展必然简单或无需验收。

## 建议的首版验证场景

至少覆盖：文档与代码一致、同条件下确有矛盾、有明确来源的条件遗漏、决策前提变化、已接受但尚未实现的需求、代码偏离需求、读取范围不足、配置/调用方改变片段含义、目标或依据在审核后修改，以及未配置 JEV、JEV 失败、Agent 与 JEV 分歧、问项方向相反。检查误报、漏报、来源定位和反馈是否可用于维护；不只检查模型成功返回。

先以一个真实模块和少量有标注的 Note/代码案例跑通“取证—核验—读取反馈—维护—复核”，保存样例、预期与实际结果，再扩展文件数量和类型。固定样例与生产引擎集成在 blueprint-review-live.test.ts，实际运行结果如下。开发验证材料可保留；生产不保留旧报告、已清理建议或处理历史，用量管理仅预留，当前不设上限。

自动化与交互验收需覆盖：普通周期与合并专项共用一个开关、默认关闭且 N=5、关闭时仍检测及标记过时但不自动调用模型或清空建议、退出暂停/重开合并补检且自动关闭时不补跑、已有有效检查点跨重启保留、临时异常只重试一次且配置错误不重试、批次保留成功结果/JEV 失败保留未核验建议、重开和 MCP 读取不无限补跑失败、仅改代码也计数但无 Note 变化不调用模型、仅 Note 时间/格式变化不被过滤、早期提交的 Note 变化被累计检查发现、审核读取 diff 外必要上下文、未配置 LLM 时的设置检测和启动提示，以及自动关闭/无 Git 差异时仍可从单篇手动入口审核。设置验收另需覆盖同页三个分区、修改后无需保存即可持久化并生效、重开后配置保留，以及无效输入/写入失败不虚报已生效、检测结果跟随最新配置。此处是完整验收范围；实际已执行和未执行项分别记录。

覆盖范围验收包括：无需指定范围即可纳入全项目三类 Note；新建文件与新子模块随提交自动参与；草稿及历史/归档文件不被排除，审核仍正确区分生命周期；Git 未变化的存量 Note 不因全项目覆盖而每轮重审。

展示与入口验收包括：当前项目/工作区/分支和输入版本正确，跨分支晚到结果与旧 MCP 请求不能覆盖新状态；合并后的新报告依据最终内容，当前未处理意见可辅助核对，已清理历史无需恢复。部分处理仍点灯、全部清理隐藏，UI/MCP/存储均无历史建议库或恢复入口；失败、漏审和旧结果不误清理或复活条目。目标删除自动清理及恢复不复活旧结果按建议管理模块验收。清理后新的独立审核可能提出同类问题，不再验收永久抑制不采纳项。右侧通过原生 MCP 读取与处理，缺少报告或过时时如实返回，不生成新审核；处理请求校验当前版本、重复关闭返回明确状态，遵循已有宿主权限。完整版本另验证自动审核静默无通知/声音，蓝图活动区显示当前阶段、进度或失败状态，节点灯不显示运行态；指南明确模块前与收尾读取约定。

## 实际取证与模型验证

审核 Agent 仅使用 review.notes（定位 Note 与代码引用）、review.paths（按路径片段查找）、review.search（字面量搜索线索）和 review.read（按行分页取得可引用原文）。目标 Note 必须完整读取后才能探索其他材料；发现结果不是已读证据。当前规则 note-review/5 按每条同仓 codeRefs 的实际路径核对是否读过对应文件，目录引用允许目录内文件；无关文件或只读部分引用不能代替尚未读取的路径。完整报告缺少必要引用会拒绝发布，材料不足须显式标记 insufficient 并说明未覆盖内容。tests/unit/blueprint-review-engine.test.ts 的 22 项通过，其中新增两项复现并阻止无关源码代替引用和多引用漏读。

路径核对只能证明打开过引用文件，不能证明所读行覆盖了全部相关分支或 symbol，也不能由静态测试证明语义判断正确。跨仓引用仍需要明确取证能力与覆盖说明。现有程序测试主要验证版本、引用、取消和状态规则；不同真实模型的参数生成、误报／漏报、长源码必要片段及跨仓材料仍需带预期结果的质量样例，不能把确定性提供方的工具传输通过视为质量验收。

当前审核由只读 Agent 首先完整分页读取目标 Note，再自主检索相关 Note、源码与测试并按需读取；不再预装关联材料，也不设置总字数、文件数、审核时长或工具调用次数上限。审核使用模型的动态上下文预算，接近窗口时自动压缩并继续；单次工具读取按行分页。程序记录实际读取的原文与 hash，引用须逐字落在已读片段；目标未读完或尚有同仓代码引用路径未读取时，不能宣称完整审核。手动审核在当前工作区取证并校验版本；自动审核从同一固定提交读取 Note 与代码，以该提交校验引用，当前工作区不同则保留建议并标为过时，审核期间目标或建议状态变更仍保护并发票据。材料不足时不允许清除旧问题。没有可证实的必要建议时允许空 findings 且 coverage 为 complete。失败的来源查找若已由 Agent 纠正，不再仅凭历史工具失败拦截完整报告；最终已读材料、覆盖与引用仍须通过校验。此前 32 文件／120,000 字符的预装取证与下述样例属于旧版验证，不代表当前 Agent 流程的实测质量。

用户指定 Vertex AI / gemini-3.8-flash。三类型五场景整轮 14/15，需求材料不足一例因不完整输出被拒绝，单独重试通过；没有将拒绝结果当通过发布。本轮另用隔离仓库实测：明确矛盾的模块 Note 生成 1 条矛盾建议；Git 自动审核在工作区有更新草稿时生成 1 条建议、失败 0 篇，并标记过时；一致的模块 Note 返回 0 条建议且覆盖完整。重复同一 Git 矛盾样例时曾出现 1 次完整覆盖却无建议的漏报，因此将规则更新为 note-review/3，明确要求核对当前实现陈述与已读代码；更新后 2 次重复实测均生成 1 条矛盾建议。样本量不足以保证模型不再漏报。运行未启用 JEV，开发配置未修改。JEV 失败/分歧/未启用以受控替身验证，真实有无 JEV 质量比较因开发凭据无法解密尚未完成。

报告存于 docs/validation/blueprint-refactor/gemini-without-jev.json 和 gemini-insufficient-retry.json；这是固定受控材料的真实模型结果，不代表所有实际工程材料的质量保证。核心程序校验、取消、过时输入、失败保留、UI 处理与 settings 均有定向测试。
