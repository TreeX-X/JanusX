# 用模块声明生成系统结构，保留决策与任务职责

## Problem

现有 Note 保存决策理由、需求和执行契约。全量文档关系图不能直接说明系统的长期模块边界；将决策改写为模块或要求每次任务维护关系，会损害决策的独立性并增加日常成本。

## Expected behavior

在既有 S1.2 initiative 中明确标记项目、模块与示例。蓝图从共同读取快照生成当前系统结构，保留全部 Note 阅读入口、显式接口与原始决策和任务导航。结构变化才同步模块声明；模块文档仅有一个维护位置，跨仓引用不复制正文或扩大写入权限。

## Scope

更新 WorkflowX 规则和模板并同步三仓；验证现有 agentX 共享包兼容性；适配 JanusX 的结构投影、界面及少量真实模块声明。保留五种 kind、已封存标准、Task 契约哈希算法与执行回执规则。不安装 Archify，不移动历史决策文件，不恢复 agentX 工作区中已有的源码删除。

## Acceptance criteria

- [x] AC-1: WorkflowX 明确项目与模块约定、单一归属和条件性同步规则；xarch、xdo、xdel、xflow 与状态读取使用同一规则，三仓双面一致。
- [x] AC-2: 现有共享读取与序列化保留模块字段；Task 契约哈希、基线和回执保持兼容，标准版本与摘要不变。
- [x] AC-3: JanusX 可切换系统结构和全部 Note；当前结构只展示已采纳的有效项目与模块，自动布局，草稿、示例、历史和诊断仍可访问。
- [x] AC-4: 模块详情可追溯原始决策与任务；接口只按显式 provider 匹配，跨仓身份保持明确，缺失或歧义不猜测连线。
- [x] AC-5: JanusX 的项目和粗粒度模块以真实代码为依据；保留既有决策与 Task 身份、正文和契约，不要求为全部历史文档补归属。
- [x] AC-6: 针对性单元与浏览器验证通过，类型检查通过；既有规范缺陷与新增缺陷分别报告。
