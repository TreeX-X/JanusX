# 知识库自动化重构：可靠采集、批量提取与易读知识

## Background

用户在 dev 中测试知识库自动化，工作一下午只有一个候选，仍需人工审核，处理记录大量积压。重构讨论将保留“采集 → 提取 → 候选审核 → 入库 → Wiki”的大流程，重新评估内部机制是否能持续产生可靠知识。本 Note 保存诊断与用户想法，机制重构处于讨论阶段，未执行旧数据清理。用户另行要求将个人画像入口调整为开发中，该展示调整与未来机制实施分别记录。

### 新会话接续说明

本 Note 是这次重构讨论的持续记录，后续会话应先阅读全文再继续，不从最早的“双提取机制”想法重新开始。用户要求详细保存讨论结论，避免会话重启后丢失前提；已确认内容、助手建议和未决问题应分别维护。用户已启动 P0，范围、契约、模块和验收已整理为 [P0 规格草案](./2026-10-07-knowledge-p0-spec--7f8e2f5d.md)，复杂样本与旧测试处置见[测试设计](./2026-10-07-knowledge-p0-validation--13f8c056.md)。整体 Ready Summary 尚待确认，P1 功能重构未开始；未执行数据删除、迁移或真实模型评测。

用户的核心目标是让持续工作能够形成可用、可读、可追溯的知识，而不是让后台任务数持续增加。低产出既暴露恢复循环等具体故障，也促使用户重新考虑提取与审核机制。现有数据只能证明采样时的故障和状态，不能据此宣称一下午只产生一条有价值的信息。

接续讨论的前提：用户已认可程序采集与 LLM 语义处理的统一流程、充分采集后组织上下文批量提取、知识条目命名、人工与自动审核并存，以及审核通过后知识才生效。用户明确要求设置修改即生效、JEV 一起重构、旧格式清理、旧测试全面分析与重新设计、复杂多样样本验证能力、卡片 UI 和内容呈现共同重设。最新 UI 边界为保留整体风格及现有左侧 tab、内部功能 tab 样式，具体见“UI 适配范围与风格边界”。

“生成 Wiki 后保留条目、Wiki 作为默认阅读入口”“有时间上限的小批触发”“固定条目身份”“上下文不足自动补取”等属于讨论中提出的建议；不能因为写入本 Note 就视为完整实现方案已获确认。继续讨论时应聚焦本文件末尾的未决问题，不重复询问已确认的产品方向。

此前的[知识库噪声与运行状态需求](./2026-10-06-memory-noise-progress-audit--81b578b4.md)及其[实施任务](./2026-10-06-knowledge-review-status-audit-plan--76ef32d1.md)记录已实现的防线与验证。本草案提出新的机制方向，不将旧实现记录改写为未完成，也不将旧测试通过视为真实自动化收益已得到证明。

### 2026-10-07 只读诊断

读取 dev 的 knowledgeSettings，以及本机 `%APPDATA%/JanusX/janusx/knowledge` 下的自动任务账本、恢复队列、观察、候选和正式知识。dev 配置启用自动化：提取与 Wiki 生成使用外部 gemini-3.8-flash，条目与 Wiki 审核使用 jev-1.13.0，阈值为 0.9。运行数据持续变化，以下为同次诊断不同读取时点的快照；历史账本数量不等于界面当前有效待办，不据此计算独立回合成功率。

| 采样项 | 结果与解释 |
| --- | --- |
| 自动任务账本 | 1,046 条历史记录；extraction 为 needs-review 962、failed 31、succeeded 2、cancelled 2、pending 6、running 1 |
| 正文尚未就绪 | 854 条任务，全部来自 OpenCode，仅对应 7 个会话/回合组合；其中两个回合分别产生 462、387 条记录 |
| 恢复队列 | 791 条记录，只对应 5 个会话/回合组合 |
| 其他阻塞原因 | 找不到恢复路径 39 条、引用校验失败 44 条、提取窗口超预算 8 条、覆盖检查不完整 6 条；均为历史记录数 |
| 候选与正式知识 | proposed 候选 1 条，历史 rejected 26、applied 5；5 条正式事实均 archived，活动工程事实 0，Wiki 页面 0 |

恢复循环有代码和数据双重证据。[transcript-recovery.ts](../../src/main/knowledge/transcript-recovery.ts)中的 entries 在恢复未完成时给 sourceEventId 追加 `:transcript-pending` 并提交观察；recoverObservationTranscript 使用该观察的 sourceEventId 再次提交恢复，submit 据此生成新的恢复身份。[automation-service.ts](../../src/main/knowledge/automation-service.ts)又为这些未完成观察安排提取与恢复。实际事件 ID 中出现数百层同样后缀，同一回合持续生成新任务。OpenCode 最初读不到回答的具体原因仍需逐回合核对数据库与时间边界，不能把错误名直接解释为用户没有产生回答。

唯一候选描述右侧 island 历史卡片重复的根因。它引用同一回答的两个副本，正文哈希一致，但一个是 assistant/model-generated，另一个是 unknown/unverified；还包含 tool-observed 来源。自动化 evidence 门禁遇到引用来源 unverified 就要求人工审核，账本原因为 source-needs-human-review，发生在模型评分之前。该候选因会话上下文变化累计产生 8 条审核任务记录，其中 6 条为上述门禁，2 条取消。降低 JEV 阈值不能修复这个来源冲突，也不能将未知来源直接改标为可信。

[extraction-context.ts](../../src/main/knowledge/extraction-context.ts)对具有会话与回合关联的窗口携带同一会话此前的非系统观察；多个窗口会重复处理历史。[extraction-run.ts](../../src/main/knowledge/extraction-run.ts)依次完成分块提取、整理、覆盖检查和最多三轮修补；覆盖检查按证据分块与候选分页组合执行。整批通过后才发布候选，局部引用或覆盖失败可能阻止其他有效条目产出。自动任务串行执行，条目审核没有单独的优先通道。以上解释了成本与反馈延迟的结构性风险，但尚未测量模型调用总成本、漏提率或完整延迟分布。

## Idea

### 用户提出的方向

1. **采用程序采集、LLM 提取的统一流程。** 用户已认可“程序采集并保存证据 → 去重与就绪检查 → LLM 提取整理 → 审核 → 正式知识 → LLM 生成 Wiki → 审核发布”。采集不依赖 LLM；未配置模型时仍可保存证据，显示等待知识处理，配置后再处理积累材料。LLM 承担语义提炼和 Wiki 编写，不以接入自主调用工具的完整 Agent 为前提。此前的双提取机制想法不再作为当前重构要求，统一结果格式的目标继续保留。
2. **知识库设置全部修改即生效。** 设置界面不要“保存”操作，不要求用户修改后再统一提交。输入校验、连续输入、失败反馈、持久化顺序及在途任务如何响应设置变化需要配套设计。
3. **JEV 审核随整体机制重构。** 重新设计其输入、审核粒度、覆盖与冲突判断、阈值含义、失败分类、重试与人工审核边界，使其适配统一数据与批量提取；不能只调整当前阈值或沿用原审核链。
4. **全面分析并处理知识库相关旧测试，重新设计验证。** 逐项识别旧机制绑定的断言、过时夹具和仍需保留的产品约束，明确保留、改写、替换或删除的依据。范围包括采集恢复、旧规则提取的去留、LLM 提取、审核、队列、设置、数据存储、IPC、UI 与端到端闭环；实际清单将在实施规划中通过全库搜索及依赖分析形成，不声称当前已完成盘点。
5. **重构时全部清理旧知识格式。** 将旧 schema、兼容分支、读写入口、测试夹具及存量旧格式数据纳入清理设计，避免长期维持新旧两套工程知识格式。P0 中用户明确选择旧工程数据“不备份，全部进行删除”，采用切换后从新采集开始，不迁移或重新提取旧工程材料。个人资料按提问范围保留至 P10；具体工程归属删除、共享引用与起始水位见 P0 规格，不在 P0 执行删除。
6. **评估积累一部分证据后交给 LLM 一起处理。** 用户提出批量处理方向，希望相邻内容能一起理解并减少碎片处理。批次边界、触发时机与等待上限尚未确定，不能将其解释为必须积累到固定数量才能处理。
7. **重新设计知识库卡片的 UI 展示和内容呈现。** 用户明确确认两者均属于重构范围：UI 将重新设计卡片布局、视觉层级、状态展示与交互；内容将重新设计标题、摘要、正文、适用条件和来源的组织与显示方式，解决当前阅读晦涩的问题。两部分需要共同设计，不能仅调整样式或仅润色文案。具体布局、字段及交互方案继续讨论，当前尚未确定设计稿。
8. **整个知识库 UI 适配新机制，同时保留现有整体风格。** 用户明确要求左侧 tab 样式、内部功能 tab 样式等继续保留。卡片与功能适配需要沿用既有视觉体系，不将本次机制重构扩大为全应用换肤；具体范围见“UI 适配范围与风格边界”。
9. **代码模块化，合理设计文件与目录结构。** 用户明确要求不要将实现堆积到一个文件。重构需要按职责、状态与依赖边界组织代码，后端流程、模型适配和 UI 各自分工；目录和公共接口设计纳入 P0，各阶段实现与验收持续检查，不能留到全部功能完成后再机械拆文件。
10. **个人画像与个人记忆机制一并重构适配。** 用户明确扩展了范围，不能再按“个人域只做共享接口兼容、产品机制保持不变”实施。Janus 人设与 Harness 是内置的，用户希望 Janus 能记住聊天中的相关内容，也能在用户明确要求记住时可靠保存并在后续使用。参考项目为 MaiBot；共享底层与独立策略的具体划分为当前设计议题，详见“个人记忆与工程知识的关系”。
11. **个人画像/记忆机制排在整个计划最后。** 用户明确要求先完成知识库功能并反复打磨，再开展个人域重构，避免个人机制跟随尚不稳定的工程知识反复返工。前期只梳理共享边界并保证现有个人域不被破坏，不提前实施个人领域的新策略。当前个人画像在创新功能页归入“开发中 · In Development”，展示分组不改变用户已保存的启用状态或已有数据。

### 根据诊断提出的机制建议（待讨论）

恢复任务将以工作区、引擎、会话和原始回合形成稳定身份，失败只更新同一状态。正文尚未就绪将留在采集恢复阶段；恢复需要期限、退避和休眠状态，不能通过派生事件绕过重试限制。完成通知将关联原始消息，避免重复正文以不同身份进入提取与审核。

提取将考虑以完成回合的增量证据为主，携带相关历史约束与纠正，合并同一会话尚未执行的重复工作。按可独立验证的条目或小批次推进，局部失败单独修复，覆盖缺口仍需明确记录；不能以缩小窗口为由丢掉后续纠正和条件。

候选身份、证据引用、范围、来源机制和当前审核状态将使用统一契约。程序将承担来源识别、通知过滤、去重与回合就绪检查；LLM 将承担语义提取、整理和文档生成。可评估为用户主动填写的结构化条目提供直接候选入口，但该入口尚未确定，不等同于恢复完整的规则语义提取管线。JEV 与宿主各自负责什么、哪些对象可自动入库，应以证据质量和产品要求确定。

### 批量处理建议（待讨论）

**重点设计项（用户已确认方向）：充分采集证据、组织上下文，再分批交给 LLM 提取。** 采集将保留用户要求、方案讨论、否定与纠正、助手回答及相关工具结果。规则将负责来源识别、会话与回合边界、去重、纯运行通知过滤、敏感信息保护和完整性检查，不再通过关键词或重复次数提前判定知识价值。原始证据充分保留不等于每次发送全部历史；提取批次将提供新增证据与必要历史，语义价值由 LLM 判断，形成候选后仍须核验。

上下文组织需要重点处理任务起始目标、有效约束、跨回合指代、最终决定及后续纠正。Hook 将作为主要触发入口的建议，完整会话记录将作为证据；Hook 去重、延迟补读和遗漏恢复仍需具体设计。历史摘要仅辅助理解，关键结论须能追溯原文；上下文不足时补取相关证据，无法补齐则标记待补而非猜测。用户确认了充分采集再批量提取的方向，具体触发阈值与补取实现仍待讨论。

提取输入建议明确分成三部分：本批完整回合的新增证据、帮助解释本批内容的必要历史上下文、用于判断重复或冲突的已有相关知识。新增证据承担主要提取对象的角色，历史上下文包括本段工作的起始目标、有效约束及前面的方案与纠正；已有知识应区分正式条目和候选，不把未核验候选当作事实依据。全文保存、摘要辅助、相关原文补取的关系需要重点设计，不能用一段无来源摘要取代原始证据。

讨论示例：先比较 SQLite 与 JSON，再由用户决定“单机部署采用 JSON”，随后助手执行并产生工具结果。提取需要将决策与单机条件保留在一起；先前的 SQLite 提议不能作为另一个已采用方案入库，助手说“完成”也不能代替执行证据。如果批次只有“按第二个方案做”，应补取方案内容而非猜测。该示例是需求说明，不是当前项目真实存储决策，也不作为期望知识写入生产库。

采集将即时持久化，模型处理将按已完成回合小批积累。优先按同一工作区、同一会话组织批次，保留相关历史条件和纠正；不因达到数量就混合无关项目或任意拼接长会话。模型请求将处理新增证据及必要上下文，避免每批重读全部历史。

触发将结合积累量、短暂空闲及最老就绪证据的等待时长，任一适用条件满足即可调度，并提供立即整理入口。最大等待计时不能被持续到来的新消息无限重置；证据不完整的回合留在恢复阶段，不阻塞其他已就绪回合。具体回合数、token 预算和时长需经样本测量确定，当前没有接受固定数值。批处理可能减少重复上下文并改善跨回合理解，也会增加等待和上下文成本，需要衡量吞吐与入库延迟，不能预先保证质量提升。

同批条目可逐项核验与推进，局部失败不要求整批重做；跨条目依赖与相互矛盾仍需一起判定。批次结束后到来的纠正通过后续增量触发相关条目复核，不能因为已完成一批就永久忽略新证据。界面将分别解释正在积累、等待模型配置、排队、处理和受阻，并展示已就绪回合数与等待时间，避免用户把积累误解为故障。

### 卡片表达建议（待讨论）

条目将优先表达“是什么、在什么条件下成立、对当前项目有什么用”。卡片可由简短标题、一两句保留关键条件的摘要、知识类型和清晰状态组成，详情再呈现原因、适用范围、来源与时间。关键例外、否定和版本条件不能因摘要简化而丢失；展开正文可完整追溯。

知识内容、系统处理结果和历史审计将分别组织。原始 JSON、哈希、内部错误码和重复执行记录不应占据知识卡片主要阅读区域，技术诊断可展开查看。候选、已确认条目与 Wiki 需要明确区别；卡片正文润色不能把模型提议显示为已确认事实。来源不足时用普通语言解释缺少什么以及用户能做什么，不要求用户理解流水线内部状态名。

可读性应同时进入提取与审核契约：条目需有明确主体，避免把多个无关结论挤成一句，保留必要术语并补足上下文。正式知识的语义改写须绑定版本并重新核验，不能为美化显示私自修改事实。后续设计将用真实但脱敏的条目比较用户能否快速识别结论、适用条件和待办动作；当前尚未制作界面原型或完成视觉验收。

### UI 适配范围与风格边界

**已确认：知识库 UI 需要配合机制重构，整体视觉风格、左侧 tab 样式及内部功能 tab 样式继续保留。** 用户原话中的“左侧 tan 样式”按同句“内部功能 tab 样式”的上下文记录为左侧 tab 样式。本约束要求沿用现有导航的视觉表达；不推断用户要求固定全部页签名称、数量或信息架构，也不擅自改动它们，必要调整应在后续设计中具体说明。

UI 适配需覆盖采集与积累状态、批量处理进度、候选人工/自动审核、已确认条目的阅读与追溯、Wiki 与来源条目的联系、设置即时生效及错误反馈。卡片的布局、正文组织、层级和动作是明确要求重新设计的部分；整体主题、配色、字体和导航控件应复用当前项目视觉体系。设计时先检查实际组件与样式来源，识别共享 tab 与主题约束，再调整知识库内部内容，不能根据描述另造一套外观。

“保留风格”不意味着保留晦涩的字段、内部错误码或与新机制不符的旧操作。用户应能分辨证据正在积累、模型正在处理、条目等待自动审核、需要人工决定及已经入库；这些状态需适配新机制，具体文案与布局待设计。设置无需保存的要求同样适用于适配后的知识库设置，不因保留旧面板风格而继续保留保存按钮。

后续 UI 验证将同时检查新功能与风格约束：真实组件交互、不同知识内容长度、空态/加载/失败/过时响应、适用主题和窄宽窗口，以及左侧与内部 tab 的视觉和交互回归。当前只确认方向并记录范围，没有制作原型、截图比较或完成浏览器验收。

### 知识条目与审核

用户已认可“知识条目”作为提取后知识单元的名称，并确认“采集原始证据 → 提取为候选知识条目 → 人工或自动审核 → 已确认知识条目”的流程。候选属于尚未生效的条目，审核通过后才作为正式知识使用。人工审核与自动审核将并存，审核结果与依据需要可追溯；系统故障、内容不合格和需要人工判断应分别处理。

| 术语 | 当前讨论中的含义 |
| --- | --- |
| 原始证据 | 采集的用户消息、助手回答、相关工具结果等；不等于已确认知识 |
| 知识条目 | 提取后知识的统一领域名称，可表达事实、决策或可复用方法 |
| 候选知识条目 | 尚未通过核验、尚未生效的条目；可查看和审核，不作为已确认知识参与常规召回或 Wiki 生成 |
| 已确认知识条目 | 人工或自动审核通过、正式生效的条目，两种审核方式进入同一知识库 |
| 知识卡片 | 条目的 UI 展示形式，不是另一种知识存储对象 |
| Wiki 草稿/页面 | 基于已确认条目组织的主题文档，草稿审核与条目审核需要区分 |

当前“候选事实”在概念上对应新流程的候选知识条目；当前 Wiki 候选应与之区分，不能把所有候选统一解释成知识条目。该对应关系仅帮助理解领域概念，不构成复用旧 schema 的决定，旧格式清理要求继续有效。

粒度建议为一项可独立理解、核验和更新的知识，必要条件和例外不拆散。审核前后保持同一条目身份、通过状态或版本变化保留审核记录是当前建议，具体实体与版本 schema 待设计。自动审核将依据证据、内容与冲突检查形成结果；人工可主动确认或接手确需判断的条目。人工入口同样需要展示证据与影响，不将提供方超时或临时失败全部转成用户待办。

当前建议在生成 Wiki 后继续保留已确认条目，提供 UI 查看及 Wiki 到条目、条目到证据的追溯；Wiki 将作为主题阅读入口，条目作为可核验与更新的知识基础。条目被替代、撤回或过期时应影响相关 Wiki，而不是因生成 Wiki 就删除条目。此处的保留方式及具体导航布局属于设计建议，尚未作为独立 UI 方案确认。

### 个人记忆与工程知识的关系

**已确认的新范围：个人画像、个人记忆及其在 Janus 对话中的使用都需要随机制重构适配。** 用户以 MaiBot 为能力参考，希望 Janus 能积累有用记忆，明确“记住”的内容能够被记住。用户已说明 Janus 的人设与 Harness 内置；本次记忆重构不以动态重写人设或执行规则为目标。用户问的是共享底层还是独立机制，以下为当前建议，尚未确认全部个人记忆策略。

现有实现证据：[user-memory-tools.ts](../../src/main/agent/runtime/tools/user-memory-tools.ts)的 user-memory.save 保存带 remember 意图的 observation 并返回 queued，工具说明明确需要在收件箱人工审核；[profile-projection.ts](../../src/main/knowledge/profile-projection.ts)仅将有效且 confirmation.kind 为 human-review 的个人事实投影到画像。[user-profile-service.ts](../../src/main/knowledge/user-profile-service.ts)已有基于事实的派生画像与手动覆盖，[user-recall-service.ts](../../src/main/knowledge/user-recall-service.ts)提供个人独立召回预算并融合画像、事实和近期事件。因此需要重新设计记忆写入和对话使用的闭环，不只是给个人画像换 UI。

参考检查基于 [MaiBot 固定提交 f9ec3670](https://github.com/Mai-with-u/MaiBot/tree/f9ec3670a3638d6a4708ee5253f7ffe2838c9415)。读取的相关实现包括：[人物事实写回与用户证据收集](https://github.com/Mai-with-u/MaiBot/blob/f9ec3670a3638d6a4708ee5253f7ffe2838c9415/src/services/memory_flow_service.py)、[人物事实原文核验](https://github.com/Mai-with-u/MaiBot/blob/f9ec3670a3638d6a4708ee5253f7ffe2838c9415/src/services/person_fact_verifier.py)、[人物画像注入](https://github.com/Mai-with-u/MaiBot/blob/f9ec3670a3638d6a4708ee5253f7ffe2838c9415/src/maisaka/memory/person_profile.py)、[聊天回想](https://github.com/Mai-with-u/MaiBot/blob/f9ec3670a3638d6a4708ee5253f7ffe2838c9415/src/maisaka/memory/mid_term.py)及画像刷新策略。源码显示这些责任分开组织，画像参与对话注入，人物事实有用户证据归因与核验。检查不等于验证完整运行效果，也不能推断用户当时参考的版本与当前提交一致；不照搬其群聊多人物处理或规则匹配策略。

#### 建议结构：共用基础能力，独立领域策略

共享证据身份与来源定位、版本化条目基础字段、存储和可恢复写入、去重基础能力、任务调度设施、模型提供方适配、检索基础组件与审核/操作日志。不同领域可共享契约外壳和基础设施，但有各自的类型、状态约束和运行策略，不强迫个人事件、用户偏好与工程事实使用完全相同的业务字段。

工程知识按项目隔离，重点是决策、约束、程序与验证依据，通过审核后用于项目检索和 Wiki。个人记忆按用户归属，重点是明确要求记住的内容、个人偏好及需要延续的经历；个人记忆不需要先生成 Wiki 才能在聊天中使用。工程任务中的一次性要求不能自动变成跨项目偏好，个人信息也不能因为共用索引被其他项目或 MCP 无差别读取。

人设描述 Janus 如何表现，Harness 约束其如何执行，个人记忆提供“对用户及过往交流的了解”。检索到的记忆是带来源、范围和时间的参考，不具有改写内置人设或 Harness 的权限；明确的新请求可以更新旧偏好，但保存偏好不是对任意未来操作的永久授权。

#### 两种个人记忆写入建议

**用户明确要求记住：即时路径。** 对“记住，我希望默认用中文回复”等直接请求，建议绑定真实用户消息、目标内容和范围，完成必要校验后作为用户明确确认的记忆保存，不再等批次积累，也不要求同一内容再进收件箱点一次批准。成功持久化并可检索后再回复“已记住”；失败或只进入队列必须如实说明。含糊指代、无法判断个人/项目范围或复杂覆盖冲突时，补取上下文或仅澄清必要信息。该路径是新建议，尚未实现；不能直接把当前工具由助手生成的内容标为用户已确认，需证明写入内容对应用户明确意图。

**自然聊天积累：后台路径。** 从完整对话批量提取个人记忆候选，区分稳定偏好、自述事实、近期事件和临时要求，使用个人领域审核策略后生效。不确定的推断保留为待确认，不能将提及次数直接视为人格结论；助手猜测、第三方描述、引用及玩笑不自动成为用户事实。是否允许自动确认哪些类型，以及 JEV 的个人事实支持性检查，仍需设计和确认。对个人自述核验的是“用户确实这样表达且含义被正确保存”，不能声称核验了现实世界客观真伪。

显式写入与后台积累共用记忆存储、版本和检索，不形成两份互不一致的个人库。实时写入应获得独立执行机会，避免排在工程长批次之后。“记住这个项目采用 JSON”应按明确项目范围处理，不因触发词为记住就写入全局个人画像；具体意图分类与冲突策略待定。

#### 个人记忆、画像和召回

个人记忆建议区分需长期保留的偏好/明确记忆，以及带时间和有效期的近期事件。不是每一条聊天内容都进入画像；画像应从当前有效、适合描述用户的记忆派生出简短视图，可以重建并追溯到条目，不另存一份不可解释的独立“人格事实”。“明天要去出差”等事件不永久固化为稳定偏好，明确要求长期记住的内容也不按一般近期事件默认过期。

对话使用建议结合少量稳定偏好和本轮相关记忆，按预算自动注入必要信息，必要时调用记忆检索；不把全部个人历史塞入每轮提示词。验收必须覆盖下一轮、新会话和应用重启后的记忆可用性，以及无关问题不误召回。保存、更正、忘记均需贯穿原始来源、有效条目、画像、检索索引和缓存；用户要求忘记后，后台重放旧证据不能无意恢复同一内容。

个人 UI 将展示“记住了什么、从哪里来、是明确要求还是自动整理、是否有效”，提供纠正和忘记入口，并在聊天中给出真实的保存反馈。画像与近期记忆视图沿用现有整体风格和 tab 样式，共用卡片基础组件但采用适合个人内容的字段；不把个人记忆强行展示为工程 Wiki。

#### 对排期和测试的影响

个人域已从接口适配扩大为机制重构，但按用户最新要求整体后置至 P10，在 P0～P9 工程知识闭环完成并经过打磨后再启动。P0 只识别两域归属和共享依赖；P1～P9 对共用部分做必要兼容及回归，保持现有个人功能与数据，不提前实施显式记忆即时保存、自然记忆自动审核、画像派生或新个人 UI。个人旧格式迁移与专用旧机制清理同样安排在 P10；工程 P8 不得删除个人域仍需使用的共享实现。

P10 建议分为两个可独立验收的工作包：个人记忆写入/更正/忘记 2～3 日，画像派生/跨会话召回/UI及专项验证 3～5 日；增量合计 5～8 个有效工作日。开始前根据打磨后的共享底层重新核对方案和估算，不将个人开发穿插到知识库迭代中。

新增关键样本：显式记住后新会话仍能使用；自然提及偏好与一次性命令区分；项目要求不晋升全局偏好；否定、玩笑和第三人称归因；用户更正覆盖旧版本；指定期限的事件不成为永久画像；忘记后重放不复生；工具失败不回复已记住；多个会话重复请求去重；个人记忆不改写人设/Harness、不污染工程检索与 Wiki。个人 JEV 评测独立标注支持性和领域归属，不能只沿用工程样本的阈值结论。

### 重点验证：复杂、多样的测试样本

**用户明确要求测试样本设计得复杂、多样，以验证实际能力。** 该要求将覆盖采集、上下文组织、提取、审核、条目生命周期、Wiki 整理与可读性，不能仅验证简单成功路径、字段格式或接口连通。以下场景矩阵为后续样本设计依据，尚未创建数据集或完成验证。

| 场景 | 样本复杂度 | 需要验证的能力 |
| --- | --- | --- |
| 长会话与跨批纠正 | 多轮方案讨论、跨批指代、后续否定、条件变更、暂停后续谈 | 找到正确上下文，保留最终有效结论及条件，复核受影响旧条目 |
| 混合来源与可信性 | 用户要求、助手提议、工具成功/失败、引用他人内容、完成通知交错；同文不同角色 | 区分提议与事实，不将助手自述当成工具验证，不因去重抬高可信等级 |
| 密集知识与低价值内容 | 多项独立结论、相关但不同条件的规则、大量日志中少量有效结论，以及确实无知识的对话 | 控制漏提、误提、过度合并与碎片化，允许有依据的空结果 |
| 条件与语义细节 | 否定、例外、数量、单位、版本、环境限制、操作顺序、中英混合及相似术语 | 精确保留含义，不能因摘要或 Wiki 润色丢失关键限定 |
| 重复与冲突 | 同义复述、重复 Hook、重复证据、同名跨项目对象、与已有知识部分重叠或冲突 | 身份稳定、工作区隔离、适当去重，区分补充、替代与真正冲突 |
| 不完整与异步输入 | 延迟落盘、缺失正文、乱序、重启、长时间持续输入、批次超预算、恢复重试 | 补读与等待有界，不制造新任务，不让未完成回合阻塞其他就绪证据 |
| 人工和自动审核 | 应自动通过、确需人工判断、应拒绝、模型超时或限流、审核中证据变化 | 审核分流正确，错误批准可识别，瞬时故障不冒充人工决策，失效快照不入库 |
| 条目与 Wiki 生命周期 | 多条目形成页面、一条目被多页引用、条目替代/撤回/过期、页面生成中来源变化 | 原文可追溯、条目与页面状态一致、旧结论不会继续作为当前知识发布 |
| 卡片与阅读 | 长短内容、多条件结论、长标题、不同状态、证据缺失、候选与正式条目并列 | 用户能读懂结论、限制和下一步，摘要无语义损失，状态不会误导 |

测试集将考虑脱敏真实会话、精心构造的边界样例及组合场景，并为关键样例标注期望知识、必须保留的条件与证据、不得产生的结论及预期审核去向。相同材料将以不同分批、重复投递和顺序扰动运行，检查最终有效知识的一致性；涉及时间与纠正的样例须按真实事件顺序解释，不能错误要求不同语义历史产生相同结论。

程序测试替身将验证身份、状态机、并发、恢复和契约；真实模型评测将验证提取与 JEV 审核能力。两类结果分别报告，不能用固定模型输出的测试通过替代真实语义能力证明。评测将关注误提、漏提、条件保留、错误批准、合理人工分流、Wiki 忠实性以及耗时和调用成本，并保留失败样例；不以候选数量或总通过率单独证明能力。具体样本规模、评判口径、模型重复运行次数及质量阈值将在测试设计中确定。

恢复、提取与审核将考虑分别分配执行预算，给近期工作和审核留出执行机会。状态展示将区分独立回合、当前任务、历史尝试、无知识结果、系统受阻和人工决策；收益将结合入库正确性、漏提情况、端到端耗时与调用成本衡量，不能只优化候选数量。

### 实施排期建议（2026-10-07，供用户审阅）

用户要求完整实施计划与排期。本节是在上述已确认方向上形成的阶段建议，仍属于 idea 草案，不代表已经执行或建立已接受的任务验收契约。正式实施任务将引用本 Note 并承接确认后的范围，不另外维护平行计划文件。当前没有启用并行代理，也没有承诺模型调用费用或实际交付日期。

排期按一名工程人员顺序实施、每阶段包含对应测试与自审估算。下表工程知识及共用底层原估算为 **23～33 个有效工作日**；个人域纳入机制重构后，建议增加 5～8 日，当前总量暂估 **28～41 个有效工作日，约 6～9 个工作周**，不含等待设计反馈、提供方不可用和进一步范围扩张时间。它是工程工作量估算，不是当前编码代理的墙钟执行时间承诺。阶段 0 完成具体盘点和数据方案后重新校准；真实模型质量与存量重建最可能影响末段排期。测试与 UI 设计从前期开始，最后阶段负责联合验收，不将测试全部拖到最后。

当前范围明确包含工程知识与个人画像/记忆两域，原“个人记忆产品策略保持现状”的排期假设已被用户的新要求替代。共享底层、独立领域策略为推荐架构；已确认条目保留供 Wiki 引用、具体默认页签暂不改变仍为待确认设计。旧工程数据不备份全部删除已在 P0 明确，个人数据保护到 P10；条目保留和个人显式记忆即时生效细则仍需确认，不能把排期假设视为用户的新决定。

| P3 LLM 提取与条目形成 | 2～3 日 | P0、P2 | 提取结构化候选，保留条件与引用，局部修复及去重；输出清晰的条目标题和正文 |
| P4 人工/自动审核与 JEV | 3～4 日 | P0、P3 | 建立统一审核状态与版本校验，重新设计 JEV 请求与结果分流，核验通过才入库 |
| P5 Wiki、召回与追溯 | 2～3 日 | P4 | 从已确认条目生成与审核 Wiki；来源变化驱动失效/更新，检索和图谱不消费未生效知识 |
| P6 设置即时生效 | 1～2 日 | P0；联调依赖 P2、P4 | 去掉保存语义；校验、持久化、乱序响应与在途任务配置版本处理一致 |
| P7 UI 与内容呈现 | 3～4 日 | P0 设计基线；联调依赖 P4～P6 | 工作台及助手入口一致，卡片与详情重设，流程状态易读，保留左侧和内部 tab 样式 |
| P8 旧格式退出与存量切换 | 2～3 日 | P1～P7 | 移除过时规则/队列/评分/读写入口；按已确定方案转换或重建数据和索引，验证不会重新写入旧格式 |
| P9 综合能力与运行交付 | 3～4 日 | P0～P8 | 真实模型评测、复杂组合场景、全链路及打包验证，产出质量与性能结果、切换及恢复说明 |
| P10 个人画像与记忆机制 | 5～8 日 | P0～P9 完成，工程知识经过打磨 | 基于稳定底层完成个人写入、审核、画像、召回、UI、旧数据适配及专项验证；整体最后实施 |

阶段顺序为 P0～P9 工程知识实施与交付，预留根据真实使用反复打磨的迭代，再进入 P10 个人画像/记忆重构；不将个人工作包插入工程阶段。打磨轮次与持续时间尚未确定，不计入 28～41 日的初步工作量，因此不能将总估算视为固定日历工期。P6 的实现和 P7 的原型可在契约明确后先行，但不假定多人并行带来的工期收益。

#### P0：建立共同契约，先准备能揭示能力缺口的样本

首先盘点所有采集源、旧确定性提取、LLM 提取、Laya/精炼链、审核、事实写入、Wiki、检索、导入导出、MCP、个人域共享代码以及 IPC/preload/renderer 消费者。盘点项需标注保留、改写、替换或移除及其依据。当前搜索测试与夹具约命中 140 个文件，包含共享或间接引用，仅为发现范围，不是确认全部需要改写的清单。

契约将定义来源身份与原文定位、回合就绪、批次边界和检查点、条目状态及版本、审核依据、Wiki 引用与来源新鲜度。候选到已确认的状态变化必须与语义版本、审核快照和来源绑定，不能让 UI 自行推断领域状态。排查 dev/installed/portable 各配置与知识根，避免假设 profile 隔离等于知识数据隔离。

#### 模块化与文件结构要求

P0 将先绘制模块职责与依赖方向，明确每个模块拥有的状态、公共接口、写入边界及测试位置，再确定具体目录。用户已确认模块化要求；以下职责划分是设计起点，不是已确定的目录清单，需结合现有复用代码及共享包归属调整。

| 建议职责边界 | 主要责任 |
| --- | --- |
| 采集与证据 | Hook/会话适配、原始消息身份、来源归因、正文补读、证据完整性与恢复 |
| 批次与上下文 | 回合积累、批次边界、增量游标、历史上下文选择及补取预算 |
| 调度 | 任务生命周期、执行预算、退避、取消及检查点协调；不包含提取提示词或 Wiki 正文生成 |
| 提取 | 模型提取输入与输出、整理、引用验证、候选形成与局部修复 |
| 审核 | 人工/自动审核策略、JEV 审核契约、结果分流与审核快照 |
| 条目与 Wiki | 分别管理知识条目生命周期和 Wiki 生成/发布/新鲜度，通过明确接口关联 |
| 提供方与存储 | 模型协议、超时与凭据适配；文件读写、原子写入与恢复等基础能力，分别组织 |
| 宿主及查询适配 | IPC/MCP 注册、检索/召回和工作台投影，调用领域接口，不复制领域状态机 |
| 前端功能模块 | 卡片、条目详情、审核操作、处理记录、Wiki 阅读及设置独立组织；页面组件负责组合，公共状态逻辑复用 |

领域契约不依赖 renderer 或 IPC 注册细节；模型协议、存储和外部会话访问通过边界接口接入。调度负责协调任务，不将各阶段的业务实现聚合进一个服务文件。条目审核与正式写入由明确的所有者控制，模块拆分不能拆散原有原子性和版本校验。前端将数据读取、交互状态与展示组件合理分离，保持工作台和助手入口共用同一状态与动作判定，避免各自维护一套实现。

拆分依据是职责与变化原因，文件行数仅作为检查信号，不设尚未经讨论的硬性行数门槛。避免把大文件机械拆成相互调用的碎片、堆入通用 utils 目录，或为每个简单操作制造一层抽象。每个新模块应能回答其责任、拥有的状态、允许的依赖和验证方式；公共入口清晰，内部实现不被其他模块任意引用。

各阶段验收需检查：核心业务未重新堆积到 automation-service/processing-queue 或工作台页面；没有新增循环依赖和重复状态机；模块测试能独立覆盖主要契约；跨模块集成测试验证组合行为；领域变更及入口调整同步到适用模块声明和 Note。旧文件逐步替换后删除过时路径，不能同时长期维护新目录与旧实现。该工作属于既有重构排期，P0 发现额外跨仓库依赖时再调整估算。

建立复杂样本的标注格式、基线指标和第一批失败样例，测试分类覆盖“保留的产品约束”“已过时的机制断言”“缺失的能力验证”。UI 先记录现有左侧导航、内部 TabStrip、主题与两个审核入口，再形成卡片和详情的设计方向；保留风格与内容改造一起评审。

#### P1～P3：先解决稳定输入，再改善提取产出

P1 将在稳定原始事件/回合身份上补读和恢复，不为一次失败创建新回合。将完成通知与正文角色分开，同一原始消息只拥有可追溯的来源身份；正文哈希相同但来源不同不能简单合并并提升可信度。补齐重复 Hook、先通知后落盘、遗漏通知、重启、并发和已有积压恢复测试；把 854 条记录来自 7 个回合的故障抽象成小型可重复夹具，不将私人会话硬编码进测试。

P2 将完成回合积累为批次，按大小/空闲/最大等待等条件触发，提供立即整理能力；精确阈值经基线测试确定。只发送增量证据与必要历史/相关知识，支持缺上下文时有预算的补取。恢复、提取和审核分配独立执行机会，限流退避、失败休眠、检查点与指标形成统一状态语义，避免多条队列互相重试或统计重复。

P3 将语义提取与确定性准入分清：模型选择有长期价值的结论，宿主校验引用、范围和结构。要求正文自包含、保留条件，标题与摘要不夸大结论；修复单项引用或模型格式错误时保留其他可用结果。跨批次重复、补充、纠正和无知识结果都必须有明确处理。是否将整理与覆盖检查合并成模型调用，将依据样本质量和成本确定，不机械保留现有多轮整批循环，也不直接删除完整性检查。

#### P4：重设 JEV 职责，保留人工与自动两条审核路径

JEV 将针对候选、实际支撑证据、有效历史条件及相关已确认知识验证支持性、条件完整性和冲突。不得仅将候选正文同时作为待审内容与唯一覆盖要求，就宣称完成了原始证据的遗漏检查；“此条正确”与“本批重要知识是否漏提”需要分别验证。

宿主保留身份、作用域、来源完整性、撤回与并发版本约束；JEV 不能覆盖这些约束。模型不确定、确定不支持、可修复引用问题、来源待补、提供方错误、需要人工冲突判断应返回不同处理结论。人工与自动通过调用同一正式入库边界，审核期间变化的内容不得按旧结果入库。阈值使用标注样本校准，保留真实分项与审核配置版本，不把分数直接称作正确率。

#### P5～P7：形成用户可读、可使用的闭环

P5 将按主题组织已确认条目，生成 Wiki 草稿并核验正文、引用和关系后发布。保留条目到证据、页面到条目的追溯；新增、替代、撤回或过期的条目触发相关页面更新或明确失效。同步改造搜索、常规召回、知识 MCP、助手上下文和图谱消费，防止候选、旧格式或失效版本重新流入正式知识。

P6 将设置变更按有效字段/配置组合持久化，开关等明确操作直接生效；连续文本输入需避免半个地址或半个模型配置触发处理。具体输入提交时点与防抖实现待设计，但不得要求点击统一保存。保存失败、快速变更、迟到返回、页面关闭及运行任务配置变化要有明确结果；降低阈值是否重审历史另行明确，不能等同于静默批准全部候选。

P7 将统一工作台、助手审核入口和相关知识预览的对象状态与动作。卡片展示清楚的标题、核心结论、关键条件和状态，详情提供完整正文、来源和审核依据；系统处理记录与知识内容分开展示。左侧导航继续沿用 KnowledgeWorkbench 的 navButton/navActive 等既有风格，内部功能 tab 沿用共享 TabStrip；不为重构重写全局主题。覆盖候选、已确认条目、Wiki 草稿/页面、积累/排队/受阻、空态与错误态；调整中英文文案、键盘导航和适用主题/窗口宽度。

#### P8～P9：完成旧机制退出与可验证交付

P8 按 P0 用户选择清空旧工程资料，不备份、不迁移、不重提取；先用合成隔离数据演练按域删除和个人保护，不复制真实旧资料作为隐性备份。具体删除集合、共享证据引用、切换水位及新空库初始化恢复由 P0 规格统一定义。逐项处理旧确定性知识提取、旧 Laya、精炼任务、旧候选快照、旧字段和相关测试；若被个人域或其他功能共用，先处理依赖再删除，不以名称含 legacy 为删除依据。工程新入口仅写新格式，个人专用旧格式到 P10 再退出。

P9 使用真实提取模型和 JEV 执行标注评测，至少报告误提、漏提、条件保留、错误批准、人工分流、Wiki 忠实性及端到端耗时/调用成本。建议首版样本为 40～60 个有明确标注的场景，覆盖九类复杂情况，再选取 10～15 个高风险组合场景做多次运行与不同批次切分；数量是计划建议，质量阈值在 P0 确定，不能将样本数冒充验证充分性。保留未用于提示词调优的评测子集，分别报告程序替身测试与真实模型评测结果。真实调用是否可运行取决于提供方、凭据与调用预算，缺失时如实标记未验证。

交付需覆盖 Hook 到 Wiki 的隔离全链路、应用重启、设置切换、来源变化、旧数据切换演练及发布构建。依据项目脚本完成相关单测、类型检查、lint、i18n、Note 检查、构建和 Electron 端到端验证，打包交付时检查包边界与运行依赖；不能只在 dev 页面上验证 UI。准备原始数据保持不变时的失败恢复与版本切换说明，在线实际切换安排在具体结果可审阅后，不包含在本次只写计划的动作中。

## Alternatives considered

保留现机制并修复恢复身份与来源去重，范围最小，能直接切断主要故障，适合作为止血方案；它仍保留全历史重复处理、整批准入和原审核成本，不能单独满足统一流程、旧格式清理与易读性目标。

完整的无 LLM 与 LLM 双提取机制能支持长期离线产出及规则可预测性，但需要维护模式切换、去重、审核适配与双路径测试。当前产品仍需要模型组织语义知识和 Wiki，用户已认可可靠采集加模型处理的统一流程，因此不再以两套完整提取机制作为首选。

程序采集与就绪检查、LLM 语义处理、统一审核与下游消费的流程符合已确认方向。它允许无模型时积累证据，但自动产出语义知识与 Wiki 将依赖模型可用性，需要清楚展示等待原因并控制积压。

逐回合立即调用模型能缩短首条反馈时间，却增加重复上下文与碎片知识；大批累积能摊薄部分请求成本，但等待长、失败影响范围大。建议采用有等待上限的小批处理，具体效果需用真实负载验证。

仅调低审核阈值、放宽证据检查或增加并发，实施成本较低，但不能修复任务自增及重复来源身份，还可能扩大调用量或引入误入库；不建议将其作为本次重构的核心措施。

## Open questions

- 知识条目的具体粒度、稳定身份、版本与状态 schema 如何设计？名称“知识条目”及人工/自动审核后生效的流程已确认，无需重新讨论命名。
- 批量处理采用何种回合数、token 预算、空闲时间与最大等待时间？跨会话相关内容是否只在知识整理阶段合并？
- 统一数据格式覆盖观察、候选、正式条目、Wiki、审核记录中的哪些对象？如何表达不同提取来源而不增加后续界面分支？
- JEV 的审核单元、条件与纠正覆盖、自动批准范围如何确定？哪些情况由系统修复，哪些需要用户判断？
- 修改即生效如何处理尚未输入完整的地址或模型配置、快速切换、持久化失败和在途请求？阈值变化是否只影响后续任务，是否触发已有候选重审？
- 旧工程“不备份、全部删除”已确认。实际执行前只核对按工程归属的精确删除集合、个人共享引用和多进程起始水位，不重复询问是否备份或迁移。
- 什么数据集用于判断误提和漏提？首条候选、最终入库的时间目标与调用预算是多少？
- 卡片默认展示哪些字段，候选与正式知识的阅读和操作有何区别？用户觉得晦涩的典型条目有哪些，应如何检验改写仍完整保留条件？
- 是否采用保留已确认条目并提供独立阅读入口的建议？Wiki 是否为默认入口？这些入口如何嵌入现有导航而保持整体风格、左侧 tab 和内部功能 tab 样式？
