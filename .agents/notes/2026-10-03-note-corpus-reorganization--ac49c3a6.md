# 全仓 Note 按模块、决策和交付职责整理

## Problem

现有项目结构已能从声明生成，但旧父域混合当前模块与交付专题，记忆、产品面、远程协作及蓝图专题尚未完整接通。后续新增文档存在独立根节点，DSH 文档混合已落地事实和待办，且不能通过正式规范校验。仅有粗粒度模块卡片不足以形成可持续阅读的工程文档体系。

## Expected behavior

逐篇盘点仓库 Note，基于正文和代码证据整理模块声明、专题归属和明确关联。当前模块描述责任边界；计划型 initiative 保留交付语义并归入对应模块；决策保留取舍，Task 保留契约。文件保持扁平命名，路径不承担模块身份。拆分混合事实与计划的文档时保留 UUID 与可追溯出处，不因画布需要改写历史状态。

## Scope

覆盖 JanusX 的 .agents/notes、必要的代码反向注释及针对文档完整性的验证。可修正不合规命名、整理已有 initiative、补充明确关系，并拆分 DSH 决策和未来需求。保留所有既有 Task 原始字节、验收编号和契约；保留未提交的知识复审需求及已有来源快照。此工作不改变运行时代码、共享 schema、其他仓库或工作流规范，不维护第二份持久索引。

## Acceptance criteria

- [x] AC-1: 全量 Note 有可复核的盘点记录；所有正式文档通过 schema、唯一身份及本仓引用检查，DSH 的六项错误消除。
- [x] AC-2: 当前模块具有真实入口与边界，旧计划和性能专题正确挂接；草稿与历史不被提升为当前实现，结构图无缺失父节点、冲突或循环。
- [x] AC-3: 逐篇审阅未关联文档和跨域文档，以明确关系建立可达性；保持历史决策原有父关系和所有 Task 原始字节及 contractHash，不按标题关键词批量猜测归属。
- [x] AC-4: DSH 的现有 UUID 保留，已落地决策与未完成需求分开，关键限制和原始事实可追溯，改名后代码及文档引用全部更新。
- [x] AC-5: 全量解析、引用与真实蓝图投影通过验证，相关 Task 执行兼容回归通过；未提交用户文件和运行时代码行为保持不变。
