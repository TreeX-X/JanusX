# 0.9.1 优先个人远程开发，CPA 延后

## Problem

个人账号在 Codex CLI 内开发可使用官方订阅登录；[OpenAI 认证文档](https://developers.openai.com/codex/auth/)将 ChatGPT 订阅登录与 API Key 访问列为不同方式。[CPA 方案](./2026-10-02-cliproxy-gateway-sidecar--23372e89.md)还包含程序下载、进程维护、七类账号登录、额度与批量管理，对主要使用个人 CLI 账号的场景增加的直接收益有限，同时需要持续适配上游。Janus 内置聊天、知识提取与审核仍读取[独立模型配置](./2026-09-18-terminal-provider-collections--51ac8035.md)，不会因 CLI 已登录而自动获得订阅调用能力。

离开开发电脑后继续查看和操作开发会话，以及将来由团队成员受控访问工作区，都需要跨设备连接与宿主授权。[远程与协作模块](./2026-09-26-remote-team-sync--b653bb34.md)已有会话网关和托管平台适配基础，完整团队身份及服务端同步仍需独立交付。同时推进 CPA 面板、远程入口和团队数据协作会分散版本投入。

## Proposal

0.9.1 将优先交付个人跨设备远程开发，以“离开开发电脑后仍能查看并继续自己的开发任务”为目标。CPA 集成将暂缓，不纳入 0.9.1，也不指定替代版本；原任务保留方案与验收项供重访。团队协作将在个人远程基础验证后逐步扩展，本决策不承诺其交付版本。此处记录已采纳的顺序，不表示远程功能已实现。

首轮远程范围应围绕连接与撤销访问、工程及会话状态读取、终端输出、补充指令、审批与停止、断线恢复和重复操作保护，以及代码变更与产物查看形成可验证的使用流程。执行仍由宿主负责，控制端通过既有网关提交授权操作；个人 CLI 的模型登录可留在执行主机，CPA 不作为远程机制的依赖。具体控制端形态、网络覆盖、操作能力与验收须在实施任务中界定；[LaunchSurface 草案](./2026-09-21-launch-surface-remote-visualization--82ff589f.md)的 GUI 嵌入、帧传输与输入控制不因远程优先而自动进入版本范围。

远程机制应为团队场景保留复用边界：连接与协议版本、调用方身份、按工作区及动作授权、状态快照与增量传输、重连与操作去重、撤销及审计。每次操作必须在宿主检查权限，已连接不能等同于拥有全部权限；个人设备身份不能直接当作团队成员身份。复用这些边界不要求在个人远程阶段实现完整多租户系统。

团队协作仍将单独处理组织与成员、角色及资源权限、共享数据的权威来源、并发版本与冲突处理、任务归属和交接。远程会话状态传输不等于共享蓝图及知识库的持久化同步；后者沿用[团队身份提案](./2026-08-20-tob-identity--ec2fb5e6.md)和[团队同步基础提案](./2026-08-20-tob-transport--abb5ed88.md)继续设计。基于 GitHub/GitLab 的异步协作可沿现有托管入口独立推进，无需等待全部远程能力。

## Alternatives considered

- 先完成 CPA 全量集成：可为内置模型调用提供统一入口并降低多账号配置成本，但个人 CLI 开发已有登录路径，完整面板投入无法直接解决跨设备继续开发的需求。
- 先完成团队协作：可直接服务多人共享工程，但身份、权限、同步、冲突和远程访问需同时设计，较难用一个个人场景先验证连接与会话操作的可靠性。有明确团队用户及共享流程需求时应重新评估此顺序。
- Do nothing / reuse：保持现有本地开发、模型配置与托管平台入口，新增维护成本最低，但跨设备继续开发仍缺少完整使用流程。

## Risks

远程优先可先验证团队会复用的连接与授权边界，但不能保证团队的数据模型可直接复用；若先把个人身份和权限写死在传输层，后续团队接入仍会返工。应分开传输、授权与业务状态，并在每次操作保留调用方及资源上下文。连接成功、界面可见和网关存在均不能替代端到端验收。

CPA 延后的代价是 Janus 内置模型功能继续依赖现有模型接入，不能宣称所有功能均可直接使用 CLI 订阅。重访信号是内置功能使用订阅成为明确需求、重复的多账号配置问题出现，或已有网关接入成本足够低；重访时应先评估最小接入范围，不能默认恢复原七类账号面板的全部工作。
