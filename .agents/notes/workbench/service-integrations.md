# 服务集成与 CPA 账号管理复用

## Intent

JanusX 通过可信扩展接入 CLIProxyAPI（CPA）的既有管理页，Figma 仍为后续候选。通用扩展基础与内置工具迁移已交付 S1、S2；S3 提供应用全局的 CPA 连接设置和中部页面。服务集成增强工具连接、配置和工作台入口，保留原 CLI 的会话管理、交互和执行逻辑。

CPA 复用既有管理前端，支持 JanusX 托管本地实例和连接已有实例。已有实例模式只保存地址，不读取或注入管理密钥；本地模式首次启用下载官方组件，支持用户设置管理密钥或自动生成，加密保存后在原版页面登录，也可显式复制当前密钥。账号授权、刷新令牌和额度查询由 CPA 管理；不自动复制 CLI 登录或修改 JanusX 模型凭据。未来如需原生额度摘要或模型 API 配置，再单独确定接口和供应商覆盖。

CPA 只覆盖接入该实例的账号与调用。CLI 直接使用自己的登录时，不能假定 CPA 已观察到其身份、请求或额度。只有出现不经 CPA 的账号需求，或工作台确实需要跨实例、跨服务摘要时，再评估只读账号视图。

Figma 作为独立服务集成候选：工作台承担连接状态、设计文件关联和打开入口；Agent 读取设计或执行操作需另行核对所选 API/MCP 能力及各 CLI 的接入方式。CPA 的模型网关与账号管理不替代 Figma 授权。

先以内部集成接口验证实际需求，再评估第三方插件开放。不同集成按实际能力声明配置、状态查询、操作入口及工具接入，不要求全部实现 Harness 会话协议。此探索关联既有 [插件架构提案](./requirements/plugin-architecture-forms.md) 与 [插件导入和调试提案](./requirements/plugin-import-debug.md)，不改写其未完成验收或授权边界。

交付顺序及测试证据归[插件平台分阶段计划](../planning/plugin-platform-roadmap.md)。文件树、Git、会话管理继续由内置定义与原宿主服务提供；CPA 使用相同视图贡献协议。当前生命周期由可信代码控制，尚无插件管理页与跨启动停用偏好；第三方导入与市场归后续阶段。

## Proposed surfaces

设置中的“服务集成”位于“应用设置”分组，与终端管理并列，选择本地托管或已有实例。托管提供启用、端口、自动更新、运行状态、启停／重启、立即更新、复制管理密钥和日志入口；已有实例保留地址与“保存并打开 CPA”。后续“插件”页再负责安装、启用、更新和卸载；服务连接和插件安装状态分别维护。

用户已确认中部工作区和右侧工作区均开放为通用插件贡献入口。中部用于需要较大空间和持续操作的页面，右侧用于紧凑工具及当前项目、文件或选区的辅助信息，轻量状态入口用于状态摘要及打开完整页面。插件可以仅提供其中一种视图，也可以同时提供两种，不要求所有插件都有界面。各界面沿用现有设置与工作台的主题令牌、字号、留白和细分隔线，保持简洁，不为每项服务另设一套卡片与视觉语言。

目标插件清单声明视图身份、标题、图标、页面入口、承载位置及应用级或项目级作用域，宿主按声明自动注册入口；接入已支持的能力不需要逐插件修改主程序。S1 已支持可信代码定义的视图注册、宿主入口、打开与关闭、内存快照恢复、停用清理和局部错误处理。插件作者维护页面内容及业务状态；第三方清单字段、独立 SDK、权限和受限通信仍待后续阶段实现，不能从可信扩展接口推导为已向第三方开放。

插件包自带页面与外部服务网页分别采用受限的承载及权限规则，共用视图注册机制；外部网页不因此获得 JanusX 插件桥或被作为远程插件代码加载。同一插件同时提供中部与右侧视图时，可通过宿主提供的受限接口共享业务状态；自动搬移视图、跨容器拖拽及双视图并行保活不由本次方向确认自动承诺。

CPA 是官方集成，待市场建立后可作为推荐项。主要用途为查看管理前端提供的额度及重置次数、时间等信息，转 API 按需使用。`janusx.cpa` 贡献应用级中部视图 `extension:janusx.cpa/management`，通过设置或中部 `+` 菜单打开；切换项目转移同一页面身份，原生网页会话复用。S3 后补充本地组件托管，仍无原生右侧额度摘要。

## CPA connection and session

默认地址为 `http://127.0.0.1:8317/management.html`，已有实例可配置自定义路径。仅接受 HTTP／HTTPS，拒绝地址中的用户名、密码和查询参数；无协议的回环地址按 HTTP，其余按 HTTPS，根路径自动补管理页。全局 `cpaSettings` 保存模式、启用、端口、自动更新和页面地址，密钥不进入该 JSON。缺少设置时为尚未启用的本地托管，旧版只有地址的配置恢复为已有实例模式，损坏设置回退默认值以便修复。

中部通过原生 `WebContentsView` 加载既有网页，不使用 iframe 或删除嵌入限制响应头。CPA 按地址 origin 的 SHA-256 前 24 位选择 `persist:janusx-cpa-*` 独立持久分区，与普通浏览器及其他 CPA origin 隔离。同一 origin 的路径共用登录；关闭页面释放视图，保留该分区的网页登录数据。跨项目、重新打开与应用重启可复用页面自己记住的登录。

网页没有 preload、Node 或 JanusX 完整桥，启用 sandbox、contextIsolation 与 webSecurity；固定 CPA IPC 仅允许主窗口主框架调用。HTTP／HTTPS 弹窗转为页面内标签，自定义协议和本地文件导航被拒绝；OAuth 等需要系统窗口的流程尚未验证，顶部保留“在浏览器打开”。打开对话框时原生视图让位，关闭和停用释放界面资源。此承载规则不构成第三方插件的权限桥。

原版前端“记住密码”控制其浏览器分区中的登录保存，该前端的存储不获得宿主安全存储承诺。托管管理密钥另由主进程使用 Electron safeStorage 加密持久化，无系统加密能力时拒绝启动；不注入网页，需显式“复制管理密钥”后粘贴登录。宿主模型凭据不使用这份管理登录。

## Managed local CPA

用户已选择首次启用下载、自定义端口和自动更新，认可托管 CPA 依赖 JanusX 运行。`src/main/cpa/installer.ts`、`runtime.ts` 和 `service.ts` 实现组件下载、进程托管与页面连接；固定 IPC 仅允许主窗口主框架使用。已有实例模式不接管或终止用户自行运行的进程。

2026-10-16 核对并运行[官方 v8.0.31](https://github.com/router-for-me/CLIProxyAPI/releases/tag/v8.0.31) Windows x64 二进制：ZIP 为 23,699,580 字节，`cli-proxy-api.exe` 为 72,586,240 字节。ZIP 摘要为 `28bde34eb33a1b03884bac1e8c1a402a25ae4eadd3c60df7ae0df53f8b281318`，管理页另行下载。安装器按平台／架构选择官方资源，限制后端 v8 与前端 v1 稳定版、固定仓库和资源地址，必须有 GitHub SHA-256 digest 并校验下载。仅提取根级主程序与 LICENSE，拒绝不完整归档，保留管理前端许可证；不执行归档提供的安装脚本或示例配置。CPA [MIT 许可证](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.31/LICENSE)允许再分发并要求保留声明。其他平台下载选择已实现，真实启动仅验证 Windows x64；未测量内存或完整打包增量。

组件位于 `app.getPath('userData')/janusx/components/cpa`，包含 `versions/`、`accounts/`、`config.yaml`、`management-key.enc` 与日志，数据根沿用应用现有安装版／便携版规则。二进制与管理页不进入 exe 或 asar；升级分离账号和配置。当前、前一与待应用版本之外的合规版本目录会尝试清理，清理失败不阻止运行。离线组件导入尚未实现。

本地端口默认 8317，允许 1024–65535 整数，管理页由回环主机与端口生成。修改运行中端口显示“保存并重启 CPA”并提示连接中断。启动前探测本地绑定，端口占用则失败并保留配置，不结束其他进程、不暗中换端口；随后真实绑定仍可能遇到竞争，按启动失败处理。已有实例模式独立配置管理页地址。

主进程串行管理操作，幂等启动，等待管理 API 认证及管理页就绪后再创建网页；下载／启动可停止，退出时直接中止下载并终止自有进程，防止排队中的打开请求晚到后重新创建页面。启动失败和崩溃显示失败状态，由用户重试，不自动无限重启。Windows 隐藏控制台，附带父进程退出监视辅助进程作为异常退出的尽力清理；未验证强杀所有相关进程的场景。

托管强制回环监听、关闭远程管理和自动管理页更新；首次生成独立 API 调用密钥，已有 API 配置保留。管理密钥由 safeStorage 加密并通过 `MANAGEMENT_PASSWORD` 子进程环境交接，不进入命令行、普通全局配置或明文 CPA YAML。子进程只继承必要环境，日志过滤凭据相关输出并轮转。账号令牌仍由 CPA 自己保存，不承诺全部账号文件由宿主加密。当前 Windows 发布版请求管理员权限，CPA 和监视器继承父进程权限，本轮未实现降权，也未以已签名安装包验证；这仍是已知边界。

本地设置提供只写的新管理密钥输入框、显示／隐藏和随机生成，保存时单独传递给可信主进程，不进入 settings、状态或响应。允许 8–128 位可打印 ASCII 字符且不含空格，避免 HTTP 请求头不支持的内容；前端与主进程均校验，非法输入在停止进程或持久化前被拒绝。留空保留现有密钥，首次未设置仍自动生成；随机按钮仅修改待保存值。保存后清空输入，原密钥不回填。运行中先停止自有实例，加密原子保存成功后更新内存并启动，关闭旧页面；账号和 API Key 保留。加密或文件写入失败保留原密钥，此时服务可能已停止，可再次启动。修改后原版前端记住的旧密钥失效，用户需使用新密钥重新登录；不会注入或改写原页面的登录存储。

Windows OAuth 已发现独立于管理登录的端口限制。2026-10-16 本机 CPA 日志显示 Codex 网页请求 `oauth/auth-url?provider=codex&is_webui=true` 因绑定 `0.0.0.0:1455` 被系统拒绝而返回 500 `failed to start callback server`；`netsh interface ipv4 show excludedportrange protocol=tcp` 与 IPv6 查询均含 `1426–1525`，Node 实测在 `127.0.0.1`、`0.0.0.0`、`::1` 绑定 1455 全部返回 `EACCES`，当时无该端口监听。上游 v8.0.31 的 `auth_files_oauth_callback.go` 固定 `codexCallbackPort = 1455`，管理页登录流程不读取 CLI 的 `--oauth-callback-port`；修改 JanusX 的 8317 服务端口无效。后端非 WebUI 流程可不启动转发器，并接受原页面已有的手动提交回调地址能力，但 JanusX 尚未实现端口预检或该流程兜底，不能宣称 OAuth 已验收。来源为同版本 `auth_files_provider_oauth.go`、`oauth_callback.go` 和 CPAMC 1.26.5；未修改系统排除范围或虚拟化服务，未发起实际供应商授权。

自动更新默认开启，运行时至多每日检查一次并暂存官方稳定前后端，下一次 CPA 启动应用。“更新并重启 CPA”立即检查、下载和重启。更新下载失败保留运行版本；新版本未就绪时恢复启动前配置并尝试当前版本，就绪后才切换 current 指针，账号目录始终保留。前后端主版本过滤及启动探测不是对未来全部小版本的兼容承诺；若供应商查询或 OAuth 后续才出现问题，仍需单独诊断。

启用保存或打开已启用的 CPA 页面时启动；JanusX 冷启动不主动运行 CPA，按需打开或点击启动即可。关闭中部 Tab 只关闭 UI；停用本地 CPA 或禁用可信 CPA 扩展时停止，真正退出 JanusX 时停止自有实例并保留数据。最小化和驻托盘不视为退出。不安装系统服务或开机独立常驻。该实现不开放第三方插件的本机执行权限，也不替代后续权限桥。

## Figma direction

Figma 候选方案分为服务连接、项目关联和 Agent 工具三部分：设置管理授权及连接状态，项目保存设计文件关联，中部打开设计内容，右侧按需展示关联文件或选中内容。Agent 通过所选 API/MCP 获取设计上下文或执行受支持的操作，并适配各 CLI 的工具配置。打开网页、通过 MCP 访问设计、运行 Figma 插件是不同能力；Figma 插件依赖 Figma 自身宿主，不能当作 JanusX 插件直接导入。网页嵌入、OAuth、读写能力和文件访问范围均未验证，不能由“已连接”推导出完整编辑能力。

## Plugin format and import direction

跨软件不存在可直接通用的完整插件包格式。VS Code、Figma 等生态各自定义宿主 API 和运行环境；MCP 可作为工具接入协议，但不自动提供 JanusX 界面、安装生命周期或工作区入口。插件市场负责发现、分发和更新，插件清单与宿主契约决定包的兼容性，应先验证包格式和加载闭环，再建设市场。

沿用现有提案的起步方向：JanusX 自有插件通过本地文件夹导入，包内包含 `manifest.json` 及构建后的界面资源，清单声明身份、版本、宿主兼容范围、权限和贡献入口。先实现导入、校验、授权、启用、使用、禁用及卸载，再评估 ZIP、远程源和市场分发。该格式及导入能力目前仍是提案，不代表已经实现，也不承诺直接兼容其他软件的插件。

现有导入草案限制首批第三方插件的网络、凭据及写入能力。CPA、Figma 优先通过官方内部集成验证连接、授权和真实工作流，再提炼第三方宿主能力；若需扩大插件权限，应明确修订原提案并补充验证，不通过单个集成绕过边界。

## Reference and limits

参考 CodexHost 提交 `1aa9f65d6abf8f15b3a390f10de0b97ad85ae847` 的 [账号设计](https://github.com/BytePioneer-AI/codex-host/blob/1aa9f65d6abf8f15b3a390f10de0b97ad85ae847/docs/product/codex-accounts.md)：当前原生 Codex 登录仍由官方管理，账号页展示身份与额度，并允许将兼容本地授权一次性复制到 Pi 的独立 Provider。凭据复制不是持续同步，共用 refresh token 的多个客户端可能互相影响登录；此实现不作为 JanusX 必须复制凭据的需求。

只读查看 CPA 提交 `0d18d3b365be000eeaee7de4615f9da596b2059d` 的 [项目说明](https://github.com/router-for-me/CLIProxyAPI/blob/0d18d3b365be000eeaee7de4615f9da596b2059d/README_CN.md)，其中提供 [管理 API 文档入口](https://help.router-for.me/cn/management/api)。S3 兼容性验证使用 [CLI Proxy API Management Center v1.26.5](https://github.com/router-for-me/Cli-Proxy-API-Management-Center/releases/tag/v1.26.5) 的原版 `management.html`，SHA-256 为 `57558cd023475674634a114824b014d3e5ac161f6f3791e3d86b6adab962a700`。该版本要求 CPA 8.0.0 及以上，调用 `/v8/management`；这不是 JanusX 对所有前端版本的兼容承诺。

S3 原前端验证使用模拟管理 API；后续托管验证使用校验后的真实 Windows CPA 8.0.31 与 CPAMC 1.26.5，确认本地启动、管理登录和配额页导航。未使用真实供应商账号，未验证供应商额度、OAuth 或重置操作。前端重置字段因供应商而异，不能承诺每个账号均支持重置次数；调用统计不等于供应商剩余订阅额度。完整命令与证据范围见阶段计划。
