# 主机维护组织与扫码申请加入

## Intent

第一版远程底座已要求支持 GitHub 和 Google 登录，详见[公网 Web 终端需求](./requirements/public-web-terminal-foundation.md)。用户提出后续组织加入流程：创建者分享二维码，成员扫码申请，组织拥有者审批，再按拥有者、管理员、成员分配权限。本文分析该流程与主机维护组织的候选实现，完整组织管理仍不进入第一版交付；功能可行性不代表公网链路已验证。

架构职责分开：第三方身份服务确认用户，组织主机保存成员和权限，外部通道辅助发现和连接信令，业务通过[WebRTC 直连基座](./public-relay-design.md)传输。开发者不自建、运维动态服务器，也不承担业务中转，并进一步追求分发后不持续运营任何身份或信令项目。主机身份适配及公共消息网络的新候选由连接基座维护，具体接入仍待验证，不把开发者名下托管项目当作零运营方案。

## Identity boundary

GitHub 与 Google 是用户选择的登录提供方，具体授权路线尚未选定。此前托管认证建议可减少运维，但仍涉及开发者配置服务项目；新的零运营目标下应并行评估由用户主机执行身份适配。无论采用何种路线，都只使用登录所需权限，不为远程登录请求仓库写入权限；主机依据供应商规定验证身份或授权结果并绑定当前会话，不能接受前端自报的用户 ID、邮箱或角色。

身份以身份签发者和稳定用户标识识别。相同邮箱的 GitHub 和 Google 登录不得自动合并；若托管认证服务支持账号关联，必须确认其关联策略，后续关联应证明对两个账号的控制。成员身份与设备身份分开，同一成员换设备需要重新绑定，不应自动新增组织成员。

2026-10-12 UTC 静态核对 [GitHub OAuth 官方流程](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)：浏览器 Web application flow 的令牌交换仍列出必填 client_secret，即使使用 PKCE 也不能把该密钥放入网页或桌面包。官方另明确 Device flow 不需要 client_secret，可评估由桌面应用或主机执行；其浏览器引导、申请者设备绑定和限流仍需验证。托管认证服务也可承担密钥保管和令牌交换，但不再作为必需架构前提。具体双提供方及跨端登录尚未联调，详见[零运营候选分析](./public-relay-design.md#distribution-without-developer-operated-services)。

## Proposed join flow

组织创建者生成稳定 organizationId 和组织签名密钥，在主机保存名称、成员、角色、资源权限、授权版本及申请记录。组织密钥需可备份和迁移，组织身份不绑定当前 IP 或主机名称。

拥有者生成限时邀请链接并显示二维码，内容包括组织标识、主机身份指纹、邀请标识及信令定位信息，不含组织私钥或长期登录令牌。二维码是申请入口，不代表成员身份或资源访问授权。邀请支持撤销；单次或限次数多人分享的规则待选，分享给多人不能沿用现有一次性邀请码语义而不说明限制。

申请者扫码打开 Web 入口，完成 GitHub 或 Google 登录。验证邀请和双方身份后，经信令建立受限连接，只允许提交和查询本人申请，不开放终端、文件或知识库资源。申请在主机持久化为 pending，重复扫码及重连复用原申请身份，不能产生重复成员；客户端自报 desiredRole 不产生权限。

拥有者在主机查看可验证的申请者身份并批准或拒绝。批准时事务性地记录成员及默认 member 角色、更新授权版本、记录审批人和结果，再签发绑定身份、设备及组织的有限会话授权。拒绝后不授予权限；邀请到期或撤销后不得受理新的申请。已受理申请能否在邀请到期后批准仍需明确。

成员收到结果并重新获取授权范围，只显示允许的设备和资源。每次操作仍由实际资源宿主校验身份、有效成员关系、资源范围和动作。被移除或禁用后，现有订阅及后续操作失效；多宿主的授权版本、撤销传播与最长期限需另行设计，不能仅凭一份长期成员证书持续访问。

## Roles and resource permissions

以下是候选三角色矩阵。用户明确拥有者审批；管理员是否可获委托审批，尚未选择。

| 角色 | 候选职责 | 边界 |
| --- | --- | --- |
| 拥有者 owner | 管理组织、审批加入、任命管理员、转移所有权 | 防止移除最后一个拥有者；转移需明确确认和原子提交 |
| 管理员 admin | 管理授权范围内的工作区、资源及普通成员 | 不自行提升角色、不操作拥有者；加入审批仍归拥有者 |
| 成员 member | 使用被授权的资源、申请加入及退出 | 不能管理角色、成员或组织 |

组织角色与资源授权分开。管理员不自动拥有成员私人终端权限；普通成员也不能仅因加入组织而访问全部工作区。资源权限需区分查看、输入、启动、关闭以及未来蓝图、知识库操作。角色在不同组织独立，组织切换更换权限上下文。

## Existing implementation and delivery boundary

`src/main/team/service.ts` 已有本机组织、一次性邀请码、成员禁用和角色管理。`acceptInvite` 当前直接写入 active 成员，没有 pending 或拥有者审批步骤。`src/shared/team/types.ts` 的角色为 owner、maintainer、contributor、viewer，身份适配器主要围绕本机邮箱密码；并非本提案的 GitHub/Google 登录和 owner/admin/member 三角色已实现。后续要明确历史角色映射、跨端身份替换和迁移，不只是在邀请码上增加二维码展示。

第一版范围继续为双提供方登录、个人设备授权、公网终端四项操作及可靠性验证。底座应分开身份、设备、资源授权与传输，保留组织和申请协议的扩展接口。完整扫码加入、拥有者审批、三角色管理和蓝图/知识库同步后续独立验收，不因接口预留自动视为完成。

## Open questions

- 托管认证服务、信令通道及 STUN 来源尚未选定，GitHub/Google 在 Web、Electron、手机浏览器与主机上的回调和凭据验证需实测。
- 主机在线才能接收申请；已落盘的申请可等待拥有者后续审批。主机离线时界面应明确无法提交，不承诺云端排队；否则需另选申请存储渠道。无 TURN 时直连失败也会影响组织申请。
- 组织主机备份、密钥恢复、迁移和失效接管，及多宿主权限撤销传播仍待设计；主机维护成员关系不自动提供离线共享数据。
- 邀请有效期、多人分享次数、到期后的 pending 处理、管理员权限和审批委托，以及既有四角色迁移需明确。
