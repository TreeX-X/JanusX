# 0.9.1 优先个人远程开发，CPA 延后

## Problem

个人账号在 Codex CLI 内开发可使用官方订阅登录；[OpenAI 认证文档](https://developers.openai.com/codex/auth/)将 ChatGPT 订阅登录与 API Key 访问列为不同方式。[CPA 方案](./tasks/cliproxy-gateway-sidecar.md)还包含程序下载、进程维护、七类账号登录、额度与批量管理，对主要使用个人 CLI 账号的场景增加的直接收益有限，同时需要持续适配上游。Janus 内置聊天、知识提取与审核仍读取[独立模型配置](../terminal/terminal-provider-collections.md)，不会因 CLI 已登录而自动获得订阅调用能力。

离开开发电脑后继续查看和操作开发会话，以及将来由团队成员受控访问工作区，都需要跨设备连接与宿主授权。[远程与协作模块](./module.md)已有会话网关和托管平台适配基础，完整团队身份及服务端同步仍需独立交付。同时推进 CPA 面板、远程入口和团队数据协作会分散版本投入。

## Decision

0.9.1 将优先交付个人跨设备远程开发，以“离开开发电脑后仍能查看并继续自己的开发任务”为目标。首版先开发 Web 控制端并打通公网连接基座，团队协作随后围绕蓝图与知识库同步扩展。CPA 集成将暂缓，不纳入 0.9.1，也不指定替代版本；原任务保留方案与验收项供重访。此处记录已采纳的顺序，不表示远程功能已实现。

首轮产品操作收敛为显示终端已有及新增输出、通过输入对话框提交内容、启动终端和关闭终端；连接与撤销访问、断线恢复及重复操作保护属于这些操作必须具备的基座能力。验收采用真实跨公网闭环：家庭网络中的宿主与蜂窝网络中的手机浏览器完成连接、查看、输入、启动与关闭；断网重连恢复状态，重复请求不重复执行，撤销访问使已有连接及操作权限失效。范围与验收由[公网 Web 终端基座需求](./requirements/public-web-terminal-foundation.md)维护。

执行仍由宿主负责，控制端通过既有网关提交授权操作；个人 CLI 的模型登录可留在执行主机，CPA 不作为远程机制的依赖。审批、独立的中断操作、代码变更及产物查看不作为首版交付要求；[LaunchSurface 草案](./launch-surface-remote-visualization.md)的 GUI 嵌入、帧传输与输入控制也不进入本轮范围。

公网方案必须满足用户侧无需复杂网络配置，以及开发者不提供或购买业务流量中转、不部署和运维动态控制服务器。用户不需要填写 IP、域名、端口，配置路由器、VPN 或托管隧道；远控终端输出和操作在两端之间直接传输，WSS Relay、托管反向隧道及开发者承担流量的 TURN 保底退出本轮候选。第一版支持 GitHub/Google 登录，并为后续组织身份和资源授权保留边界。[主机组织提案](./host-owned-organization.md)分析创建者主机维护组织、二维码申请、拥有者审批和三角色管理，具体机制仍待验证，不扩大首版个人远程终端范围。现成托管认证、设备发现和少量信令服务可评估，但具体依赖、配置、额度和费用尚未确定；不能把终端内容混入信令转发，也不能把凭证登录视为公网寻址已经解决。详见[公网直连设计草案](./public-relay-design.md)。

WebRTC DataChannel 加自动 ICE/STUN 是当前直连技术建议，具体接入方案及依赖仍待验证。真实家庭网络与蜂窝网络闭环继续作为必验场景，同时记录网络条件和直连证据。没有中继保底时，部分 NAT、防火墙或禁止 UDP 的网络可能无法连通，应明确反馈失败并允许重试，不承诺所有公网环境都可连接。后续若要求这些网络也能连接，需要重新讨论约束，不能静默恢复付费或托管中转。

用户进一步希望软件分发后开发者不再持续运营身份、目录或信令服务项目。托管后台方案不能直接解释为满足该目标；[零运营候选分析](./public-relay-design.md#distribution-without-developer-operated-services)保存主机身份适配和公共信令网络的评估。具体依赖、一次性应用注册及静态 Web 托管是否可接受仍待明确，不据此撤销首版双提供方登录、Web 入口或自动连接验收，也不宣称已找到完整可用方案。

局域网对应能力暂缓开发，已有实现保留，后续作为公网服务不可用时的保底连接方式。当前排期以此决策和公网 Web 需求为准，[历史 LAN 决策](./tob-lan-remote.md)中的 LAN 优先、组网到中继的分阶段顺序不作为本轮开发前置条件。后续 Android 与 iOS 可复用 Web 的设计规范、协议和业务逻辑，具体 PWA、WebView 容器或原生路线尚未确定。

远程机制应为团队场景保留复用边界：连接与协议版本、调用方身份、按工作区及动作授权、状态快照与增量传输、重连与操作去重、撤销及审计。每次操作必须在宿主检查权限，已连接不能等同于拥有全部权限；个人设备身份不能直接当作团队成员身份。复用这些边界不要求在个人远程阶段实现完整多租户系统。

后续团队协作在本轮讨论中的目标是蓝图与知识库同步，具体同步冲突问题留待后续讨论。远程会话状态传输不等于这些数据的持久化同步；身份、权限、共享数据的权威来源与版本策略仍需结合[团队身份提案](./tob-identity.md)和[团队同步基础提案](./tob-transport.md)继续设计，原提案中的自动合并或离线队列策略不视为本轮采纳。多人终端、控制权交接及任务协作流程不因该同步目标自动进入版本范围。基于 GitHub/GitLab 的异步协作可沿现有托管入口独立推进。

## Alternatives considered

- 先完成 CPA 全量集成：可为内置模型调用提供统一入口并降低多账号配置成本，但个人 CLI 开发已有登录路径，完整面板投入无法直接解决跨设备继续开发的需求。
- 先完成团队协作：可直接服务多人共享工程，但身份、权限、同步、冲突和远程访问需同时设计，较难用一个个人场景先验证连接与会话操作的可靠性。有明确团队用户及共享流程需求时应重新评估此顺序。
- Do nothing / reuse：保持现有本地开发、模型配置与托管平台入口，新增维护成本最低，但跨设备继续开发仍缺少完整使用流程。

## Consequences

远程优先可先验证团队会复用的连接与授权边界，但不能保证团队的数据模型可直接复用；若先把个人身份和权限写死在传输层，后续团队接入仍会返工。应分开传输、授权与业务状态，并在每次操作保留调用方及资源上下文。连接成功、界面可见和网关存在均不能替代端到端验收。

跨端问题需要在实现前显式处理：当前本机账号存储与本机签名密钥不能直接提供统一跨设备身份；前端对 Electron IPC 的依赖需要通过客户端接口隔离；手机后台暂停连接后须重新同步；终端输出回放、尺寸变化、中文输入与移动键盘需要实际验证；浏览器缓存清除、授权撤销及协议版本差异需要有明确行为。上述问题集中记录在公网 Web 需求中，具体解决方案仍待设计。

CPA 延后的代价是 Janus 内置模型功能继续依赖现有模型接入，不能宣称所有功能均可直接使用 CLI 订阅。重访信号是内置功能使用订阅成为明确需求、重复的多账号配置问题出现，或已有网关接入成本足够低；重访时应先评估最小接入范围，不能默认恢复原七类账号面板的全部工作。
