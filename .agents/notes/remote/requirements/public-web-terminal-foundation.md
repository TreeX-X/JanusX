# 公网 Web 终端连接基座

> 当前方向已转为 Android 原生无中继 P2P 实验，见[实验决策](../android-p2p-lab.md)。本文保留历史讨论和原验收，不表示浏览器优先或中继方案仍在实施。历史 NAT 推断不应泛化为所有 CGNAT 网络均不能直连。

## Expected behavior

首版先开发 Web 控制端，用户通过公网连接自己运行 JanusX 的宿主，在授权工作区中显示终端已有及新增输出、通过输入对话框提交内容、启动终端和关闭终端。终端执行与 CLI 登录保留在宿主，浏览器通过宿主网关请求操作；关闭指结束该终端实例，退出页面或连接中断本身不触发关闭。

连接、资源授权、撤销访问、断线恢复和操作去重属于首版基座。浏览器重连时恢复状态与输出，已结束的终端不得重新显示为运行中；请求结果不确定时查询操作结果，不能通过重新生成请求身份造成重复输入、重复启动或重复关闭。

“只做基座”以真实跨公网使用闭环为标准，宿主和控制端处于不同网络，控制端无需安装 JanusX 桌面应用。不能仅以本机回环、同一局域网、页面能显示或连接建立成功证明交付。

用户侧无需复杂网络配置，开发者不提供或购买业务内容中转。产品负责账号登录后的设备发现和自动连接协商；终端内容及操作直接在控制端与宿主间传输，不经开发者或开发者购买的 Relay/TURN/托管隧道转发。身份、授权、设备状态和协商信令可使用轻量服务，但不能通过该服务绕过业务流量直连约束。

开发者不部署、运维动态账号、组织、设备目录或信令服务器。第一版支持 GitHub 和 Google 登录，Web 控制端与桌面宿主接入可验证的第三方身份；登录成功仍需设备及资源授权。身份按签发者和稳定用户标识识别，不因邮箱相同自动合并账号或授予权限。现成托管认证及少量信令通道仍需评估依赖、服务配置、额度和费用，未要求完全消除外部服务。由创建者主机维护组织是待验证候选，不把完整组织管理加入首版范围。身份凭据与组织标识不能替代公网发现及信令交换。

进一步目标为用户下载后开发者无需持续运营身份、目录或信令服务项目。开发者名下的托管后台只能降低运维，不能直接宣称满足零运营目标。主机身份适配与公共信令网络是新候选，尚未验证；是否允许一次性应用注册、静态 Web 托管及公共服务依赖仍需明确。该目标未撤销 GitHub/Google 登录、Web 优先或用户无需复杂网络配置，当前不存在满足全部约束的已验证闭环，见[连接设计](../public-relay-design.md#distribution-without-developer-operated-services)。

公网覆盖以实际网络条件验证。直连无法建立时明确显示连接失败并允许重试，不要求用户设置路由器、网络地址或安装、配置 VPN，也不自动启用业务中继。首版不承诺任意公网环境都能连接；AC-1 的真实跨公网成功闭环仍必须完成，失败案例另行验证。

## Cross-device issues

| 问题 | 当前依据与需要界定的行为 |
| --- | --- |
| 跨设备身份 | `src/main/team/service.ts` 当前使用本机账号存储及本机签名密钥；不同机器使用相同邮箱不代表同一可信身份。需要确定统一身份或独立设备授权方案，首版不要求完整多租户系统。 |
| Web 与 Electron 边界 | `src/renderer/src/services/remote-peer.ts` 直接调用 `window.electron.peer`。Web 控制端需要可替换的客户端接口，把 UI 与 IPC、网络适配分开；本地测试网关不能直接作为公网产品能力证明。 |
| 浏览器身份与凭据 | 需要界定浏览器授权保存、退出、缓存清除及撤销后的行为。设备标识不等于用户身份，也不能单独授予操作权限。 |
| 移动端后台与弱网 | 手机后台、锁屏和网络切换可能暂停或断开连接。执行状态留在宿主，回到前台后重连并同步；后台持续在线与系统推送不作为首版承诺。 |
| 终端输出恢复 | 要区分已有输出回放和新增输出，处理序号、重复帧、缓冲截断及状态重置。首版不承诺无限历史，回放范围需在实现设计中明确。 |
| 终端交互 | 验证手机窄屏、滚动、中文输入法、组合输入及软键盘；界定本地与远程尺寸变化的处理方式，避免不同视口相互覆盖。输入对话框提交不自动扩展为逐键输入终端。 |
| 协议兼容与能力差异 | Web、宿主及未来移动应用可能版本不同。握手需要版本与能力信息；不支持的操作必须明确反馈，不能静默失效。 |
| 公网直连覆盖 | 自动穿透需要实测 NAT、IPv4/IPv6、公司防火墙和运营商网络。没有 TURN 保底时可能失败，不能通过偷偷中转来提高成功率；需要记录实际选中的直连路径及失败原因。 |

这些问题已记录为实施约束或待设计事项，尚不表示对应方案已经选定或验证。

## Acceptance criteria

- [ ] AC-1: 宿主处于家庭网络，手机使用蜂窝网络，手机浏览器无需安装 JanusX 桌面应用即可完成授权连接；未授权连接与操作被拒绝。
- [ ] AC-2: Web 控制端能列出授权范围内的终端，显示已有输出并持续显示新增输出，运行及结束状态与宿主一致。
- [ ] AC-3: 用户在输入对话框中提交内容后，内容准确到达选定终端；中文组合输入正常，重连或重复请求不造成重复提交。
- [ ] AC-4: 用户可以在授权工作区启动终端，并在 Web 中看到其状态和输出；相同启动请求重复到达时只创建一个实例。
- [ ] AC-5: 用户可以关闭选定终端，宿主结束对应实例，Web 显示结束状态；重复关闭请求不影响其他终端，也不产生新的实例。
- [ ] AC-6: 连接建立后主动断网再恢复，Web 重新同步终端状态与可用输出，避免重复追加回放；断线期间已关闭的终端不得恢复为运行中，断线本身不关闭终端。
- [ ] AC-7: 宿主撤销控制端访问后，已有连接的输出订阅及后续操作均失效；重新连接不能恢复已撤销权限。
- [ ] AC-8: 终端查看、输入、启动和关闭在宿主检查调用方及资源权限，操作保留请求身份和可追踪结果；协议或能力不兼容时明确反馈。
- [ ] AC-9: 用户通过登录、选择设备及必要的授权即可发起连接，不需要输入 IP/域名/端口、配置路由器、VPN 或托管隧道。
- [ ] AC-10: 跨公网验收提供实际传输路径证据，终端输出及操作直接在两端之间传输；开发者不提供或购买业务流量中转，首版无 TURN 或业务内容的信令转发回退。
- [ ] AC-11: 在无法直连的网络条件下，界面有明确失败及重试状态，不重复执行操作、不无限显示连接中；该失败验收不代替 AC-1 的成功闭环。
- [ ] AC-12: 自动公网连接流程无需开发者部署或运维动态控制服务器；验收列明第三方身份、发现、信令及 STUN 依赖和必要配置，不把免自建服务器描述为无需外部服务或零成本。
- [ ] AC-13: GitHub 和 Google 均可用于 Web 控制端及桌面宿主登录；身份经可信验证后绑定正确用户和设备，伪造、过期或不属于当前应用的凭据被拒绝。不同提供方相同邮箱不自动获得彼此账号权限，OAuth 客户端密钥不放入 Web 或桌面分发包。

## Deferred scope

局域网对应能力暂缓开发，已有 HTTPS、配对及发现实现保留，后续作为公网服务不可用时的保底。具体发现、直连与回退策略留待该阶段设计，本轮不要求 LAN 联调或自动切路。

后续团队协作目标是蓝图与知识库同步，数据权威来源、权限、并发版本和同步冲突策略另行讨论。本轮只保留可复用的连接、身份、授权及事件边界，不实施数据同步，也不预先确定自动合并、CRDT 或离线写入策略。

后续组织加入候选为分享二维码、登录后申请、拥有者审批，再按拥有者/管理员/成员授予资源权限，详见[主机组织提案](../host-owned-organization.md)。二维码不直接授予成员身份，完整扫码申请和角色管理不进入本轮交付范围。

后续 Android 与 iOS 可共享 Web 的设计规范、协议与业务逻辑；PWA、WebView 容器或原生 UI 的选择仍待讨论。审批、独立中断、代码变更与产物查看、多人终端控制及 LaunchSurface 投影不属于本轮必交范围。

## Transport questions

当前建议采用 WebRTC DataChannel 自动公网直连，ICE/STUN 辅助候选地址发现和连通性检查，首版不配置 TURN 中继。HTTPS/WSS 可用于账号及少量信令，信令交换结束后的终端输出与操作通过两端数据通道传输；WebRTC 可承载纯文本及结构化操作，不要求音视频。

宿主与控制端身份、资源授权、请求去重、事件恢复仍属于 JanusX 协议。WebRTC 自带加密传输不能替代远端身份确认，信令会话需要绑定经验证的账号和设备。具体宿主端 WebRTC 接入、控制服务部署、STUN 来源及自动穿透覆盖尚未验证，见[公网直连设计草案](../public-relay-design.md)。
