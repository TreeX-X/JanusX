# 个人开发工作台与团队产品的演进方向

## Intent

记录个人工具与 ToB 团队协作之间的研发取舍，以及工具箱和外部服务接入的探索。用户要求保存思考，不代表已确认策略、预算或交付范围；本文为 draft idea，不修改已有版本排期，不证明功能已交付。

## 当前判断与依据

建议下一阶段继续以个人开发者为主要用户，研发逐步向小团队共享工程上下文靠拢，暂不全面启动 ToB。演进路径为个人 AI 开发工作台、小团队共享工程上下文、由明确客户需求推动的团队产品。

JanusX 已拥有多终端、会话续接、Worktree、蓝图、Note、审核和用量统计等能力。下一阶段需要验证哪些组合形成每日使用习惯，减少用户重复解释项目、恢复工作和核对约定的成本。仓库资料不足以证明当前用户留存、付费意愿或企业需求成立，不能以功能数量代替产品验证。

全面团队化会引入身份与权限、共享数据归属、同步与冲突、成员退出、部署升级和持续支持。值得验证的购买理由是：新成员和新 Agent 能快速理解项目约定，多人并行后工程知识仍准确，交接与审查有依据。远程终端控制服务个人跨设备使用，也可成为后续基础，但不等于团队数据同步已经完成；当前边界归[远程模块](../remote/module.md)。

## 建议投入与团队试点

探索性投入建议为个人核心体验 60%、蓝图与 Note 闭环 25%、小团队试点 15%。比例只表达优先级，不是工期估算，也未成为版本承诺。个人核心关注安装配置、终端稳定性、原生会话续接、项目切换和重启恢复；蓝图关注约定读取、维护和审核能否减少遗漏。

团队首个试点可选两个人接力完成同一个项目任务：A 留下项目约定、改动原因和待办，B 在另一台电脑通过自己的 Agent 理解并继续开发，审核发现实现与约定的偏差，两人通过现有 Git／PR 流程处理修改。优先利用仓库内 Note 与已有托管平台，观察断点，再判断专用同步、权限系统和团队控制台是否必要。Git 能承载版本与审查，不自动解决语义冲突或访问控制。

几个独立团队持续使用、反复提出同类需求，且负责人愿意为交接、审查或知识维护成本付费，是提高 ToB 投入的信号。若已存在愿意付费并共同试点的客户，应优先围绕其一个具体问题交付。尚需补充活跃与留存、核心路径成功率、支持成本、实际团队客户及付费意愿证据。

## 工具箱扩展的筛选原则

工具优先解决开发过程中高频的切换和交接问题，能够复用项目上下文，并可把结果交给 Agent 或现有工程流程。浏览器、Markdown、CPA 已有入口，内置扩展基础已交付；第三方导入、凭据接口和市场仍有后续阶段，见[插件平台计划](plugin-platform-roadmap.md)。

可靠性证据分开记录：Markdown 专题记录草稿仅驻留内存、耐久保存待实现，本轮检索对应 store 未找到持久化入口，因此属于待实际验证的重启丢失风险或能力缺口；工具箱打开延迟与长会话资源占用已有用户反馈记录，见[性能记录](../workbench/long-session-performance.md)，当前是否仍存在需复测；关闭重开、重启恢复是建议检查的维度，不能仅凭提出检查就认定有 Bug。本次讨论未运行工具箱或复现这些故障，不能把历史记录写成当前实测结论。

新增候选可依次验证：轻量 HTTP 请求与响应查看、项目服务与端口／日志管理、Issue／PR 的上下文接入。HTTP MVP 可保存请求、配置环境变量并把响应或错误交给当前 Agent；是否覆盖认证、集合和自动测试待定。服务管理应复用已有运行配置与进程能力，Docker 只在真实容器工作流需要时扩展。Issue／PR 接入应先复用已有 GitHub／GitLab 托管适配。上述均为建议，具体归属、优先级与验收未确认，不重复承诺已有规划能力。

## 开发功能候选

用户要求记录以下开发功能，暂不指定版本、工期或启动实施。后续设计前先核对已有实现，只补实际缺口；此处不将候选能力列为当前缺失或已确认需求验收。

### 项目服务管理

面向同一项目中的前端、后端和后台任务等运行进程，复用已有运行配置、项目启动与进程管理。候选操作包括启动、停止、重启，查看运行状态、访问地址／端口、退出原因和对应日志，以及从服务直接打开预览页面。

优先探索“服务报错 → 将所选错误日志附加到当前 Agent 对话 → 排查修复”的短流程。日志保留来源服务与作用目录，发送内容可查看，不默认收集或发送全部日志。多服务按依赖顺序启动在真实需求出现后再细化；Docker 容器管理独立评估，不将全部进程能力重建为新系统。

### Issue／PR 上下文接入

复用 GitHub／GitLab 托管适配，把问题与审查信息连接到日常 Agent 对话：选择 Issue 后读取正文和讨论，将用户选定的内容及来源链接作为任务背景；开发后结合需求与代码改动生成 PR 描述草稿；读取 Review 评论时保留文件、行位置及所关联的代码版本，过期评论明确标记或提示核对，再交给 Agent 处理。

优先探索“审查意见 → 携带对应代码位置交给当前 Agent → 修改与验证”的短流程。Agent 上下文交接需区分 JanusX 自有 Agent 与外部 CLI，不能假定所有终端共享工具或授权。读取、生成草稿、发布评论、创建 PR 和合并分别表达；读取不隐含发布或执行修改。连接配置、平台覆盖及具体写操作范围待设计确认。

### 轻量 HTTP 调试

保存并执行请求、配置环境变量、查看响应和失败原因，把选定响应或错误交给 Agent 分析。初步只围绕项目接口调试；认证方式、请求集合、自动测试及凭据处理需要单独定范围。既有排期中的 HTTP 基础通信层不自动等同于面向用户的请求调试界面。

## Notion 接入的含义与候选范围

Notion 插件不是单一能力，可分为四层：网页或链接入口；通过 API／MCP 给 Agent 搜索、读取或写入的工具；把指定页面关联到项目并显示来源的上下文连接；本地 Note 与远端页面的同步。四层可以分别交付，网页登录成功不证明 Agent 已获授权，安装 MCP 不证明所有终端都可使用。

建议先验证“关联一份 Notion 需求，Agent 按需读取，完成开发后把交付摘要写到指定页面”的工作流。读取与写入分开授权；首步可仅做指定页面读取、来源链接及手动刷新，写回作为后续明确动作，不自动覆盖整个页面。Notion 保留产品需求／沟通材料，仓库 Note 保留工程约定，通过引用关联；不默认复制整库或建立双向同步。

需要独立核对服务 API／MCP 的实际能力、页面访问范围、所选 CLI 的配置与授权、凭据归属、内容格式和刷新策略。JanusX 自有 Agent 与外部 CLI 是否共享连接尚未决定；不能由工作台登录推导为各 Agent 自动获得访问。第三方插件网络与凭据能力需遵循后续宿主权限设计，不能照搬可信 CPA 的宿主权限。双向同步另需定义真源、远端修订、删除、格式损失和冲突处理，因此不建议作为首版。

## Open questions

优先用户是独立开发者、已有小团队还是明确企业客户？目前哪条核心路径带来持续使用，哪项阻塞最常见？工具箱候选中 HTTP、服务管理、Issue／PR、Notion 哪个已有真实需求？Notion 的首要对象是需求文档、团队知识还是任务数据库？这些答案决定投入顺序，当前尚未收口。
