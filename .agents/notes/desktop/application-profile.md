# No-install application data belongs to the user profile

## Problem

The Windows no-install executable previously created a sibling `data` directory on every normal launch. Removing it discarded settings and conversations, and moving the executable created a separate profile. The owner requires user-directory storage, legacy compatibility, and cleanup without a traveling-data mode.

## Decision

Packaged no-install builds use `appData/JanusX-Portable` (`%APPDATA%\JanusX-Portable` on Windows). Installed builds retain Electron's default profile and development retains `JanusX-Dev`. Explicit `--user-data-dir` overrides and hook/smoke clients bypass legacy migration. There is no sibling-data mode or fallback to the installed profile.

Normal startup acquires the destination's single-instance lock before importing application stores. A sibling `data/janusx` directory identifies a legacy source. Migration rejects overlapping or redirected roots and links within the profile. It copies durable and unknown files, preserves empty directories, verifies SHA-256 content, then rechecks the source inventory before deleting anything. Local-model and Python/server settings pointing within the source are relocated in `janusx/config.json`; paths outside it and conversation text are unchanged. Browser cookies, Local Storage, IndexedDB, partitions, model files, and SQLite sidecars are preserved.

Only known root caches, Chromium/partition caches, logs, crash reports, stale process locks and write probes are disposable. They are not imported. After verification, cleanup unlinks inventoried files individually and removes empty directories; it never recursively deletes a generic `data` folder. Unknown data is copied, not classified as disposable. A source-specific receipt under `.legacy-profile-migrations` records verified source hashes before cleanup. When old files cannot be removed, retry recognizes prior imports without replacing newer settings or resurrecting intentionally deleted data. Cleanup failures warn and retain leftovers; migration/conflict failures stop startup with a dialog naming both paths.

## Alternatives considered

- Keep sibling storage or add an opt-in traveling profile: conflicts with the owner's requested product behavior.
- Use the installed profile: merges single-instance ownership and settings between distributions.
- Delete the old directory or copy caches wholesale: respectively risks data loss or carries unnecessary disk usage forward.
- Overwrite destination conflicts or guess JSON merges: may destroy newer settings or journal history. Both copies instead remain available for explicit resolution.

## Consequences

The exe directory stays clean on fresh launches; legacy directories disappear after successful migration and cleanup. The executable alone no longer transports personal data. Migration discovers only a source beside the executable, so upgrade in place after closing older builds; it does not scan the disk for other copies. First migration needs disk space for a verified copy and time proportional to profile size, including local models; hashes use a bounded one-MiB buffer. Changes during copying abort deletion, but this does not provide a transactional snapshot of an actively running older build. External CLI hooks are regenerated by the existing terminal launch installer on the next terminal start.

Conflicts, unsupported links, malformed configuration or interrupted copy artifacts may require manual recovery; the source remains intact. Cleanup of read-only files retries on subsequent launches without forcing permissions. The receipt is retained to prevent stale imports; no bulk cleanup or migration of other historical profiles is introduced. Revisit when a supported profile entry is added or cross-computer import becomes a product requirement.

Verification: `npx vitest run tests/unit/application-profile.test.ts tests/unit/profile-migration.test.ts` covers 18 cases, including user-profile selection, preservation and cleanup, conflicts, copy failure, changing sources, junctions, path relocation, retry after cleanup failure and non-resurrection. `npm run typecheck` and scoped ESLint passed. Executable packaging and real-user upgrade acceptance are separate from these filesystem tests.
