# 从模块声明派生系统结构，保持决策与任务独立

## Problem

工程 Note 主要保存决策及其理由。把全部决策、需求和 Task 同时铺在画布上，难以读出系统的长期边界；将决策改写成模块会丢失文档职责，将每次工作都转成模块维护又会增加无关成本。

## Decision

系统结构使用既有 initiative 和明确的项目、模块标签，遵循 [WorkflowX 模块约定](note://d2499d5b-4ceb-4d46-aa3b-18e5c9b86034/0700e5e2-50f4-4265-a2d8-59f5d52a8c5c)。当前视图只纳入 accepted 的有效声明；示例、计划和历史仍可从全部 Note 访问。未接入仓库、缺失或冲突的父关系、接口匹配失败必须保持可见，不能按名字猜测关系。

投影复用共享 Note 快照，保留完整来源图供详情、任务操作和定位使用。结构画布仅使用派生的模块节点、父关系与显式 provider 接口。任务依赖和正文提及不变成运行时调用。结构布局与折叠在本次视图内使用，不写回源 Note，也不覆盖全部 Note 的本机布局。项目和模块卡片不把声明状态呈现为任务执行进度。

决策和相关工作根据显式关系、祖先链与验收引用查询，按来源实例去重，点击后读取原始 Note。相关列表不拥有 Task 的 parent、契约、执行状态或回执。完整 Note URI 加来源 checkout 负责消歧，模块绑定的实现仓库不能取代声明所在仓库。

本仓粗粒度声明复用合适的父域 UUID，补充职责、代码入口和实际接口。既有决策与 Task 保持原文；计划型父域不因导航需要自动变成当前模块。跨仓声明只有一个维护位置，日常工作只在职责边界、公开接口、明确依赖或已记录入口变化时同步声明。

## Alternatives considered

- 新增 module kind 可以提供专用校验和更清晰的类型名称，但当前字段已能表达所需结构。采用现有字段的约定，避免修改封存标准和共享执行契约；当模块约束无法由消费层合理表达时再考虑正式类型扩展。
- 直接接入 Archify 适合生成和分享交互 HTML，但仍需从 Note 映射组件、关系与布局，且不能替代 Task 的来源和回执。原生蓝图复用现有读取、详情和执行入口；导出功能可在独立需求下增加。
- 维持全部 Note 图是改动最小的选择，也保留最完整的工程关系，但无法提供清晰的模块总览。全部 Note 继续作为完整阅读入口，模块声明增加一个可重建的结构视图。
- 用目录路径或代码扫描推断全部模块关联可减少显式声明，但多仓 checkout、重叠职责和任务依赖会产生歧义。当前结构采用显式关系；代码路径仅承担已声明的定位作用。

## Consequences

模块文档需要在系统结构变化时维护，图本身无需人工画线或保存第二份事实。标签为可选约定，未分类的历史 Note 不会自动获得模块归属。结构视图提供粗粒度组成和接口连接，不声称穷尽运行时拓扑或自动证明代码符合全部声明。

验证由 [实施任务](./2026-10-03-module-structure-view--785a2a8e.md)记录，覆盖正式文档兼容、来源保持、父关系与 provider 消歧、视图切换及原始 Task 导航。结构投影不能绕过已有 Task 验收与事务规则。
