## 用户已明确的方向

这次工作是跨 WorkflowX、agentX 和 JanusX 的系统性重构。先确定规范，再安排实施；目前不开始运行时代码修改或旧 Note 迁移。

用户随后明确当前阶段可以开始调整，并要求先说明 WorkflowX 修改方案。推进顺序仍为 WorkflowX → agentX → JanusX；具体实施应遵循本稿已确认约束。

WorkflowX 整个 harness 的描述必须简洁干练，节约 Agent 导入文本的 token，避免本轮细节导致技能大量膨胀。功能规则需要完整，运行时默认导入的说明应尽量小；不能把讨论过程和所有边界条件直接堆入 SKILL.md。

WorkflowX 后续应按模块及子模块维护文档，允许重构文件夹和文档，包括调整归属、改名、拆分和合并。文件应具有时间标识并可以持续更新；用户反对日期起手、根目录平铺、随工作不断新增文件的组织方式。目标是文档清晰、可长期维护，并尽量控制膨胀。

agentX harness、JanusX 蓝图解析以及 Chat 重新接入 agentX harness 都属于重构范围，不能仅修改目录或提示词。

旧 Note 的批量重构必须作为独立任务，安排在解析验证任务之前。这是任务依赖约束，不意味着移动前无需盘点和制定迁移规则，也不意味着提前省略解析能力的适配。

想法、决策、任务三类需要保留。用户将 Task 定义为实施过程的沉淀文件，其职责需要在新规范中认真设计。

Task 仅由指定工作流生成，平时使用 xdo 不生成 Task。不能把 Task 设为每次修改的默认文档，也不能为简单的 xdo 工作先建 Task 再承载需求。其他工作流的具体生成时机留待工作流规范细化。

xdo 应判断本次修改是否影响已记录的文档事实。纯格式调整或完全不影响已记录事实的内部修改，可以不修改任何 Note；不得为了满足归档要求制造无信息增量的正文或更新时间变化。职责、机制、接口、约束或决策等已记录事实发生变化时，应同步维护相关文档。用户已明确同意这一例外。

文档组织采用大模块包含小模块的层次。大模块目录根部仍可有多份本层 Note，并与子模块目录共存。上层文档需要表达整体背景、机制和跨子模块关系；拆成小文档不一定能完整表达这些内容，因此上层文档可以保留完整叙述，不能被强制简化为索引。这里不要求每层只能有一份 module.md，也不要求每个主题都下沉到最小子模块。

用户已确认上述层次组织方式。WorkflowX 应自行判断何时需要扩充模块或子模块目录，何时在现有目录中维护文档，不要求用户逐次指定目录结构。用户重构模块后，文档必须正确表达实际的新结构、职责与关系，包括必要的目录和文档调整。

Agent 的自主整理受用户当前讨论和变更范围约束。只有用户谈及其他模块并提出想法或更改，才扩展到该模块的维护；不能借一次局部工作主动整理无关模块。若发现超出当前范围的关联问题，应报告，不自行扩展修改。

尚未明确的设想或待讨论的重构方向放入 Idea，不提前改写成模块的当前事实。已经形成模块规划的内容可以进入标明规划状态的完整模块文档，由 Agent 持续补充。Requirement 类型明确保留，承载需要的行为和验收依据；各类文档通过引用衔接，避免复制完整方案。

保留并统一 wiki 索引机制，让 Agent 能直接、快速发现和读取相关文档。该机制需要与新的模块组织、Note 引用和文档重构同步，不能只服务界面。Agent 维护文档时应处理现存引用的一致性。索引的具体实现和存储形式尚未确定。

wiki 机制也必须进入 WorkflowX 的规范设计，不能仅由 JanusX 界面或 agentX 的局部实现定义。具体规范与工具边界需要三仓统一。

模块目录与文档 kind 是不同维度。此前助手提出用 module 替换 initiative 的建议尚未采纳；不能因为需要模块目录就直接认定必须新增或替换 Note 类型。

采用一模块一入口文档：每个模块有一份明确入口，承载整体说明并对应蓝图模块节点。本层其他 Note 和子模块目录可以同时存在，不受此约定限制。入口文件名和元数据形式尚待规范设计。

规划模块的文档也采用完整结构，遵循同样的一模块一入口及层次组织方式。Agent 随讨论、设计和实施推进，持续补充维护同一套文档。完整结构不要求在规划阶段填满所有内容；尚未明确的部分应如实标示，不能虚构事实。规划、进行中与已实现内容应可区分，具体状态表达由规范设计。

用户同意表达模块的规划中、部分实现、已实现及已退役状态；状态名称与字段形式可在规范中确定。同一模块文档可同时包含当前事实和规划内容，正文必须清楚区分。不能仅因某个 Task 完成就自动把整个模块标为已实现。

“部分实现”目前保持抽象表达，不要求建立细粒度能力清单、完成比例或自动推导机制。

每次重新维护文档都要刷新更新时间；创建时间保持原始含义。只读不刷新更新时间。xdo 经判断无需修改文档时，不为制造记录而刷新时间；实际维护文档时必须更新。时间精度及自动写入方式由实现规范明确。

Idea 可以在意图成熟后转换为 Requirement、Decision 等适当类型，不强制复制出多份文档再保留活跃 Idea。类型转换时如何维护身份、已有引用及类型专属字段，由新规范统一设计。

## 现行机制与问题

现行五类为 idea、initiative、requirement、decision、task。initiative 同时承担项目、长期模块和阶段性专题；模块当前设计说明分散在 initiative 和 decision 中。class 表示工程工作类型，lifecycle 表示状态，两者都不等于模块目录。

现行规则要求优先原地更新，但又要求新 Note 平铺在 .agents/notes/。文件名通常以首次创建日期起手，稳定身份由 UUID 和 Note URI 承担。模块关系主要依靠 parent 和显式关联。

已检查的 WorkflowX schema 只有 created，没有 updated，且不允许任意新增字段。JanusX 至少一个新建入口直接生成根目录路径，部分蓝图投影把 created 同时用作 updatedAt。具体共享运行时的改动范围尚待完整调查。

## 助手提出、尚待用户确认的分类方案

建议从文档职责而非目录形式出发，讨论 module、requirement、idea、decision、task 五类。module 可以替代目前承担多种职责的 initiative，提供长期维护的模块主文档；原有阶段性 initiative 需要逐篇判断去向，不能批量改类型。

module 描述当前职责、边界、结构和重要接口；requirement 描述明确需要的行为、约束与验收依据；idea 保存尚未成熟的想法；decision 保存设计选择及其理由；task 保存一次有边界实施的范围、关键实施事实、验证证据、结果与遗留问题。

这五种职责不意味着每个模块都必须建立五份文件。按内容需要创建独立文档；模块层可以有整体说明和多份覆盖本层职责的 Note，子模块文档展开局部细节。原建议“简单工作的目标由 Task 承载”仅可能适用于本来就生成 Task 的工作流，不能适用于 xdo。独立 requirement 的创建条件仍需讨论。

Task 的实施沉淀不宜变成逐轮对话或命令流水账。它可以从实施前的范围和验证安排，演进为实施中的关键发现，以及完成后的交付事实和证据。同一任务持续维护，新的独立任务不覆盖旧任务。长期有效的模块事实和重要决策应同步到其归属文档，Task 用链接引用。

对于 xdo，助手建议直接维护相关模块层或子模块层的已有 Note，只有出现独立的新内容才新建适当类型的文档，不额外创建实施沉淀 Task。不影响已记录事实时可以不修改 Note，已获用户确认；具体新建判断规则仍需在新工作流规范中细化。

目录演进的初步判断建议：优先维护现有文档；现有目录内出现值得独立表达的主题时可新建 Note；形成明确、持续的独立职责，且集中组织相关文档有助于理解时，再建立子模块目录。文件数量和篇幅仅作为整理线索，不作为自动拆分阈值。不创建缺少实际内容和职责的预设目录。

模块重构后的同步建议：先确认实际发生的是改名、移动、拆分、合并、退役还是内部实现调整，再维护模块整体说明、受影响的局部文档和显式关系。保持概念连续性的移动或改名应保留身份；拆分和合并需判断哪些原概念延续、哪些是新概念，不能机械复制 UUID。修复引用并保留仍需解释旧实现的历史依据。尚未落地的新结构应明确标为计划，不能提前写成当前事实。

上层说明负责表达重构后的整体边界和协作方式，下层说明负责具体机制；跨模块主题放在能完整表达其范围的适当层级。内部实现修改不必导致目录变化。xdo 仍不创建 Task，文档调整属于其相关 Note 维护；生成 Task 的工作流可在 Task 中沉淀迁移与验证证据。

持续维护不等于只保留当前结论：改变设计方向时，应保留理解旧实现所需的决策依据；修改需求时，应保护既有验收引用；文档合并和拆分时，应确定旧身份与引用的处理方式。

## 本轮用户回答与收敛

允许存在通用 Note。蓝图整体设计等设计说明是否直接写入模块文档，需要进一步权衡；用户没有要求此类内容必须拆成独立通用 Note。最终 kind 枚举、模块文档与通用 Note 的形式尚未确定。

假定目录和文档只由 Agent 维护管理，不考虑用户手动移动文件的交互或兼容场景。Agent 仍需在自身执行移动、拆分、合并时维护路径和关系的一致性；该技术责任不能因排除手动移动而省略。

蓝图首先呈现由模块文件组成的纯模块结构，普通 Note、Idea、Requirement、Decision、Task 不混入初始模块结构。尚未实现的模块也必须呈现，不能默认只展示已实现模块；需要明确区分规划结构与当前事实。单击模块展开内部结构，双击进入详细查看，并且能够返回。不能将此前助手建议的“进入后以模块正文为默认主体”当作已确认要求；详细视图的具体呈现、展开状态与返回状态仍需在界面设计时细化。

Task 必须结合工作流设计，在迭代期间即被使用并持续记录、维护，也是移交给下一位 Agent 读取的文件，完成后成为沉淀资产。它需要支持接续工作，不能仅作完成总结；具体粒度和内容结构应从工作流派发、迭代与移交需要推导。xdo 不生成 Task 的约束继续成立。

同一任务的多个 Agent 围绕同一份 Task 迭代和移交，Task 是共同资产；不因更换 Agent、评估或修复轮次而建立另一份移交文件。确有独立交付边界时如何拆分子任务，以及并发修改同一资产的协调方式，仍需结合工作流具体设计。

用户明确 Task 仍由主 Agent 作为调度者维护。子 Agent 返回实施、评估或修复结果，由主 Agent 整合任务的当前状态、发现、证据引用和下一步；共同资产不意味着多个子 Agent 自由覆盖 Task。受控状态服务的技术写入方式需与此职责保持一致。

Task 必须在每次交接前由主 Agent 更新，确保接手者读到当前进展、结果、未解决问题和下一步；不能只在整个工作结束后补写。

跨会话接续是必须达到的能力。原会话关闭后，下一位 Agent 应能从仓库中的 Task、引用文档、代码及正式证据理解当前状态并接续工作；允许重新检查环境，不依赖原聊天记录或上一位 Agent 的私人上下文。应将这一场景纳入重构验证。

harness 与移交流程是本次重构的重点。设计新机制之前，必须重点理解既有工作流的派发、接手、迭代、评估、修复与结束流程，调查 Task 契约、输入来源、执行状态和验证证据如何贯穿其中，再确定保留与调整的部分，不能仅凭新的文档目录重新发明移交机制。此处是用户要求的前置调查，尚未完成。

持续维护文档时，Task 应能区分原执行依据与最新文档，识别影响本次工作范围、接口或验收的变化。格式和时间更新不能直接等同于目标改变；历史执行和验证证据不能随源文档更新而被覆盖。具体版本、摘要和变更判断机制必须结合现有 harness 设计，不提前确定实现方式。

用户已确认规划模块也按完整文档结构设计，由 Agent 逐步补充维护。规划模块拥有明确入口及规划状态，并在蓝图呈现；相关 Idea 保存设想和待解决问题，不承担整套模块结构的替代职责。规划模块文档可以承载未来设计，但必须明确其规划属性，不能表述为已实现事实。具体状态和关联形式尚待规范设计。

允许 Agent 自行决定清理、删除、重构或重写旧 Note，尤其是年代久远且难以维护的内容。不要求所有历史文档永久作为独立文件保留。实施方案需要说明现存有效引用与执行证据的处理方式；该要求不应被解释为一律禁止删除或需要逐篇向用户确认。

Chat 接入所指的是 agentX 提供的工程基础能力，包括 harness read/edit 等工具、脚本执行等，以及与新 WorkflowX 一致的 Note 机制。接入不能缩减为只增加模块上下文读取，也不能未经确认扩展成所有聊天入口都必须自动执行工作流。具体入口复用此前相关设计，实施前应先检索既有决策和代码。

WorkflowX、agentX、JanusX 三个仓库均要求重构，用户已确定按 WorkflowX → agentX → JanusX 逐仓推进。迁移期兼容方式应结合依赖提出方案；“逐仓推进”不等于用户已选择长期维护新旧两套格式。

用户随后明确同意：xdo 做纯格式调整，或完全不影响已记录事实的内部修改时，允许在判断文档影响后不修改任何 Note。该问题已解决，新规范应取消此类工作必须落 Note 的要求。

## 模块文档与通用 Note 的进一步建议

助手建议模块文档承担该模块当前整体设计，包括职责、边界、必要的内部结构、主要协作流程和对外接口。读者应能通过它理解整个模块，而不是必须拼接多个子文档。项目根同样可以有整体说明。

通用 Note 用于需要独立维护的深入主题或补充说明，不强制为每个设计主题创建。某段设计与模块整体高度相关时，直接维护在模块文档中；主题具有独立阅读需求、变更节奏或较多局部细节时，再拆为本层 Note，并在模块文档保留理解整体所需的摘要与关系。篇幅本身不构成必须拆分的理由。

模块文档解释当前设计如何工作，Decision 保存值得独立追溯的选择和理由，Task 保存指定工作流的实施及验证沉淀。三者可相互引用，避免完整复制同一事实。此建议尚待用户确认，不预先确定 module 是否为新 kind。

## 重构检查要求

用户明确要求重构后必须检查。旧 Note 批量重构仍安排在解析验证之前；仅完成文件迁移或 schema 校验不足以证明重构完成。

检查应覆盖模块入口与层级、规划和部分实现状态、移动合并删除后的有效引用、wiki 索引与原文的一致性、Chat 通过 agentX 读取编辑文档及调用工程工具，以及下一位 Agent 是否能凭 Task 和明确引用接续工作。应在理解现有 harness 移交流程后制定相应验证场景。

以上是检查范围要求，尚未执行验证，不能据此声称现有实现或迁移结果已通过。

## 既有移交流程的初步调查与新问题

已阅读 WorkflowX 的 modules/02-bus-payload.md、modules/09-dispatch-adapter.md、specX、执行持久化标准，以及 JanusX 的 task-brief.ts、execution-adapter.ts、independent-review.ts、desktop-executor.ts 相关部分和 agentX CLI 的 harness-mode.ts。本次只确认这些规则和调用点，尚未完成共享执行内核及 harness 实现的全面调查，也未运行测试。

既有链路在派发前固定 Task 范围、验收引用和必要决策版本；接手时校验执行依据。Main Agent 和状态服务拥有 task.execution 的更新权，实施 Agent 按允许范围工作并返回结果。局部修复继续使用同一任务，通过精简 Repair Packet 派发；跨任务问题以精简集成信息进入后续任务。此机制与同一 Task 作为共同资产相容，不要求所有 Agent 都能直接覆盖任务状态。

JanusX 的移交摘要从 Task、验收引用、被验证文件清单和有限历史生成，引用会重新核验，摘要不是另一份长期维护的 Note。独立评估入口有意排除实施者的历史轨迹，依据验收、实际代码和证据判断；新 Task 内容设计需要维持这一边界。

执行标准将 Task 和正式验证回执作为可携带资产，将本地运行、租约、对话和恢复日志作为运行协调数据。持续维护 Task 不能覆盖历史回执，清理旧 Note 也需要明确处理引用的证据。下一位 Agent 接手所必需的事实，应可从 Task、明确引用和正式证据恢复，不能只藏在本地对话记录中。

实际冲突：JanusX prepareTaskRun 对 xdo/xdel/xflow 都收集 Task baseline；agentX CLI 的 /harness <task> 支持并默认使用 xdo。新规则要求日常 xdo 不生成 Task，因此需要明确 xdo 的基础工程执行与 Task 工作流执行的边界，不能仅修改技能文字。用户尚未确认已有 Task 能否主动选择 xdo 执行，不能擅自把“不生成 Task”扩大为“一律禁止读取或处理已有 Task”。

用户已明确主 Agent 维护 Task，并要求跨会话接续。普通 xdo 不依赖也不生成 Task；用户明确指定一份已有 Task 时，允许使用 xdo 执行并维护这份 Task。该行为已获得针对性确认，不再待定。

## 收尾设计中需要覆盖的边界

以下区分用户已确认的规则与后续需要细化的设计检查项。

- 已确认：已有 Task 切换为 xdo 时允许由主 Agent 直接实施，保留原有验收条款和独立评估要求；只有用户明确调整时才改变要求，不能仅从模式名推断。
- 已确认：Task 每次交接前更新。进一步设计应区分已验证事实、报告但未验证的结果、仍在进行的工作和下一步；突然中断后的接手者应重新检查实际状态。
- 已确认：“部分实现”先保持抽象，不增加细粒度完成度模型。一份 Task 完成不代表整个模块已实现；放弃规划的整理方式仍由后续规范细化。
- 三仓逐个推进需要兼容过渡方案：新规范、工具支持、旧文档批量迁移和最终解析验证之间的依赖应明确，不能让未升级的读取器把新文档误读为有效旧文档。
- 讨论稿应在正式规范起草前整理为当前已确认要求、尚待设计的规则与证据来源，清除已失效建议和重复问答，避免把讨论历史当作并行有效规范。

## 技能体积与上下文开销约束

用户明确要求整个 harness 描述简洁干练，减少默认导入文本和重复读取。以下为助手据此提出的实施方法，具体组织在改造中核验。

- 入口只保留路由、必要边界和定向读取指引；常规任务不默认加载完整标准、全部模板、迁移说明或历史背景。
- 一项规则有一个权威归属。noteX 承担文档维护规则，orchestrateX 承担流程与调度规则，Task 契约和移交由专门契约定义；其他入口只给必要引用，不重复整段正文。执行边界处仍需保留防止越权或误判所必需的短约束。
- SKILL.md 提供可执行的短流程，细节按真实触发条件读取；不能只把长文拆成很多文件、却要求每次全部读取。
- 标准、schema、样例和校验器承载字段定义及机械约束。Agent 读取与当前任务相关的片段；不得因控制文本量而省略必要的验收依据或约束。
- 子 Agent 派发提供 Task 定位、当前动作、允许范围、必要固定引用和期望输出，避免重复粘贴完整技能、整篇模块文档及多轮对话。修复沿用已有精简派发机制。
- Codex 与 Claude 两端规则保持等价，每次执行只读取所在端需要的内容。同步覆盖面增加不应转化为单次上下文重复导入。
- 改造时清理被新机制替代的强制平铺、日期命名、无条件落 Note 等旧规则，优先整合已有技能，不为每个新概念新增技能或检查阶段。
- 验证既检查规则完整性，也比较普通 xdo、已有 Task 的 xdo、xdel/xflow 派发与修复等典型路径的实际导入文件及文本量。报告计量口径；字节数或字符数只能作为代理，不能冒充精确 token 数。用户尚未指定数值预算。
